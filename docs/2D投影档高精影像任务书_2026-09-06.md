# 任务书：2D 投影档用上「高精」瓦片影像（按片分桶的纹理网格）

日期 2026-09-06。执行者：Opus。发起人：朴东旭。本任务书自带全部上下文，不依赖对话历史。用户要求：**最佳效果**，不是最小改动。

## 0. 一句话目标

2D 平面图在**除等距圆柱之外的五个投影档**（墨卡托 / 等积地球 / 罗宾逊 / 阿尔伯斯 / 方位等距）下，影像底图选「高精」时**真的画瓦片金字塔（L0–L6）**，而不是像现在这样悄悄换成 16K 整幅；同一缩放下选级与等距圆柱**同一个公式**（同 z）；屏上清晰度从「中国全图起就顶到 16K 的 45.5 px/°」提到「L6 的 113.8 px/°」；导出 PNG / PDF 走同一份几何。等距圆柱 2D、3D、16K / 8K 两档、GRD 填充、静态层调度**一个字节不动**。

## 1. 现状与根因（2026-09-06 读码 + 按常数算账；执行前只需复核 §1.1）

### 1.1 现在的路

- `src/viz/imagery.js` 的 `imageryForFlat(k, proj)`：`proj !== 'equirect' && s.tiles` → 换成 `PROJ_IMAGERY = 'bm16k'`。调用方 `src/pages/ConstellationMap3D.vue` 的 `applyImagery()` / `imageryWantUrl()`（约 4775 / 4821 行）据此把 2D 喂成 16K 整幅、3D 仍喂瓦片；`setMapProj` / `resetCrs` 换投影都重跑它。
- `src/viz/flatmap/flatCoverage.js` 的 `drawImagery()`（约 914 行）投影分叉：

  ```js
  if (!PJ.identity) {
    if (!imgEl) return false
    if (drawImageryGL()) return true
    return blitReprojected(reprojectRaster(imgEl, null, true), 1, imgBright, true)
  }
  ```

  **只吃 `imgEl`（整幅图），`imgSet`（瓦片集）在投影档下压根不看。**
- 结果：五个投影档下点「高精」与点「16K」画面完全一样（都是 16K 整幅经 `srcThumb` 缩到 ≤ 8192 再贴 GPU 纹理网格）。

### 1.2 为什么当初这么定，以及那条判据哪里错了

2026-09-05 四修的口径（记忆 map-2d-projections）：「2D 放到头也就 0.006°/px，16K 是 0.022°/px、L6 是 0.0088°/px —— 差距只在 >23 px/° 之后才看得见」。按代码常数重算：

| 量 | 值 | 出处 |
|---|---|---|
| 2D 基准 | base = min(cw/360, ch/180)；1920 CSS 宽 → 5.33 px/° | `fit()` |
| 缩放上限 | SCAP = exp(ln 0.9 + 1.2·(ln 60 − ln 0.9)) ≈ 139× | `SMIN / SMAX / TMAX`（约 2485 行） |
| 2D 到顶 | 5.33 × 139 ≈ **741 CSS px/°**；DPR 1.5 → **1111 设备 px/°**（0.0009°/px） | 上两行相乘 |
| 16K 整幅 | 16384 / 360 = **45.5 px/°**（0.022°/px，2.45 km/px） | `IMAGERY_SOURCES` |
| L6 瓦片 | 0.5625 / 2⁶ = 0.00879°/px → **113.8 px/°**（978 m/px） | `imageryTiles.res` |
| L5 | 56.9 px/° | |

「0.006°/px」低估了一个量级还多，且没乘 DPR。**屏上超过 45.5 设备 px/° 起，16K 就是纹素被放大**：1920×1080 @ DPR 1.5 下「中国全图」（60° 宽）就是 48 px/°，再往里 16K 一个纹素占 2～24 个屏幕像素，而 L6 只占 0.4～10 个。所以「高精 = 16K」在最常用的国家级视角上是**看得见的损失**，不是理论差。

两条今天才成立的前提：

1. **GPU 路已落地**（6be5bf9：`glRaster.js` + `rasterMesh.js`）：投影档影像已是「一份三角网 + 一次 drawArrays」，平移 / 缩放 0 重烘。当初「瓦片要先拼成整幅再重投影、多一层重采样、卡」的顾虑里，「卡」那一半已经不存在。
2. **静态层已真静态**（c21ef87 / 29f1131）：影像只在手势静止后那一次重建里画，瓦片到货走 `tilesDirty → rebuildAtRest`。本任务的一切成本只落在那一次重建里。

### 1.3 历史上那一版为什么删（别再走回去）

065c321 曾做过 `tileRegionImage` + `meshWindow`（瓦片先拼成一块等经纬 **2D 画布**再整份重投影；c21ef87 删除，代码在 git 里）。它的问题全是「拼图画布」这一物本身带来的：模块级 3200² 画布（≈ 40 MB 画布内存，多实例会把 canvas 挤白）、`TR_MAX_PX` 一封顶就降一级（某些缩放下比 16K 还糊，正是用户报的「高精比 16K 糊」）、可见窗口靠 `meshWindow` 正算采样估（方位等距对跖圈附近不可靠）、每次重烘整块重拼、再走 CPU `warpTri`。**本任务书不重建拼图画布**，见 §2。

## 2. 结论：能支持，最佳方案是「按片分桶的纹理网格」

| 方案 | 做法 | 否决 / 采纳理由 |
|---|---|---|
| A 拼图画布（065c321） | 瓦片 → 2D 画布 → 当整幅源走 `reprojectRaster` | 画布内存、封顶降级、每次整块重拼、CPU 路 —— §1.3 |
| A′ GPU 拼图 | 瓦片 `texSubImage2D` 进一张窗口大纹理 → 现有单纹理程序 | 要一张 ≤ 8192 的窗口纹理（宽视角被迫降级）、REPEAT / CLAMP 两套、窗口靠命中测试估、每次重建整窗重传、显存 50～150 MB |
| **B 按片分桶** | **网格照旧规划一次（S = 整幅世界），按三角形落在哪片瓦片分桶；GPU 每桶一次 drawArrays 绑该片纹理、片外像素 discard；CPU（导出）每桶用该片图 warpTri** | **规划器一行不改；哪些片要取由分桶结果直接给出（不靠命中测试）；纹理只有可见片（20～70 MB），平移只补新片；任意缩放不撞纹理上限；跨 ±180 与 L0–L2 补边靠「经度周期 + tileClip 有效窗」统一处理；与 3D 的「一片＝一个扇区」同一思路** |
| C 每片独立网格 | 像 3D 那样每片各自规划 | 邻片细分数不同 → 片边 T 形接点 → 亚像素裂缝；方位等距的平面网格天然跨片，做不成 |

采纳 **B**。它把「瓦片」压成一个纯函数（分桶）加一套多纹理着色程序，其余复用现有的 `planRasterMesh` / `rasterFrame` / 复用判据 / 静态层调度 / `getTileOrParent` / `loadTiles`。

**能高到哪（诚实边界，写进报告）**：

- 屏上：z 与等距圆柱同式 `pickZoom(1/(k·dpr), imgMaxZ)`，L6 封顶（离线包只切到 L6；L7 是包体积决策，不在本任务）。> 113.8 设备 px/° 之后瓦片与 16K 一样是放大纹素，只是放大倍数小 2.5 倍。
- 投影自身的放大区（墨卡托高纬 1/cos φ、方位等距对跖圈 γ/sin γ）纹素被同比拉大，16K 同样存在，本任务不做逐片 LOD 补偿（§10 可选项）。
- 极区 / 对跖圈附近源纹素被压缩（一个屏幕像素盖多个纹素）：靠逐片 mipmap + 各向异性过滤，与现有整幅路（`LINEAR_MIPMAP_LINEAR`）同一手段。

## 4. 设计

### 4.1 选级：与等距圆柱同一个式子

投影档下 `z = pickZoom(1 / (kk·dpr), imgMaxZ)`（kk = `k()`；平面单位 ≈ 度：W 恒归一到 360，五档在中央经线 / 赤道 / 圆心处 1 单位 ≈ 1°）。与 `imageryPlan` 里等距圆柱的 `pickZoom(1/(kk*dpr), imgMaxZ)` 逐字相同 → **同一缩放、六个投影同一级**（§6 的一条验收）。导出时 `dpr = pixelScale`，自然选深。整帧一个 z，不做逐片 LOD（§10）。

### 4.2 纯函数 `binByTiles(M, z, set)`（新文件 `src/viz/geo/tileBins.js`，Node 可测）

输入：`planRasterMesh` 的 `{xy, uv, n}`（S 必须是整幅世界 −180..180 / −90..90；uv 可越出 [0,1]：跨接缝的两遍复制）、级 z、集名（取 gutter）。输出：

```
{ xy: Float64Array, uv: Float64Array, n,   // 分桶后逐三角形（含复制）；uv 已换成【该片全跨度】的归一坐标
  bins: [ { z, r, c, first, count } … ],    // 按 (r, c) 排序、连续区间；first / count 以三角形计
  tiles: [ { r, c } … ] }                   // 去重后的片集（ensureImagery 直接喂 loadTiles）
```

规则（每一条都要有测试）：

1. 顶点经度 `lonU = u·360 − 180`（**不逐顶点折回**，保持一格内连续），纬度 `lat = 90 − v·180`。
2. 对每个三角形取经度范围 [lo, hi]、纬度范围；对周期 p ∈ {−1, 0, +1}：`lon' = lon + 360p`，与 [−180, 180] 相交为空则跳过；相交部分落到哪些列 `c = floor((lon' + 180)/span)`、哪些行 `r = floor((90 − lat)/span)`（端点按 `tileRange` 的口径减 1e-9 再 floor，再钳进网格），逐片发一份复制；换算 uv 用**该片 `tileBox` 的全跨度**（含 L0–L2 的补边）与 `west − 360p`：`u' = (lonU − (west − 360p)) / span`，`v' = (north − lat) / span`。**用周期而不是「列号取模」**：L0 / L1 的列数 × 跨度 = 576° / 432° > 360°，取模是错的。
3. 只分给 **`tileClip` 有效窗**与三角形相交的片（L0–L2 边缘片补边那一段不算有效内容）；行列越界的不发。
4. 同一三角形落到几片就复制几份 —— 每份只画得出自己片内的那一部分（GPU 靠 discard、CPU 靠源矩形在图外画不出），合起来正好互补；边界在 uv 空间是同一条线、两份共用同一组顶点 → **无裂缝**。极点附近经度跨度大的格会落到很多片，是少数几格，认了。
5. 规划器给的「跨接缝画两遍」复制在分桶后可能重复落到同两片 —— 不去重，不透明叠画无害；测试只钉「每片得到的复制里 uv 与有效窗相交」，不钉复制数。
6. 输出确定性：同输入 → 逐字节同输出（排序键 (r, c, 原三角序)，不用 Map 迭代序）。

### 4.3 GPU 路（`glRaster.js` 加第二套程序，整幅那一套不动）

- **不改现有程序 / `setTexture` / `render`**：16K / 8K 两档在投影档的 GPU 出图要与改前**逐像素 0 差**（`pxdiff` 闸）；混进一个带分支的着色器会动浮点舍入，别省这一份。
- 新程序：顶点同一式子（`aPlane / aUV` + `uK / uTx / uTy / uDpr / uW / uH`）；片元：

  ```glsl
  if (any(lessThan(vUV, vec2(0.0))) || any(greaterThan(vUV, uWin))) discard;  // uWin = (fx, fy)：tileClip 有效窗
  vec2 t = uUvOff + vUV * uUvScale;            // 祖先片回退：整片 (0,0)/(1,1)；祖先则 (u0,v0)/(u1−u0,v1−v0)
  fragColor = texture(uTex, (vec2(uG) + t * 512.0) / uN);   // gutter：内容区落在 [G, G+512]/N，与 3D tileTexture 的 offset/repeat 同一式
  ```

  贴图 `LINEAR_MIPMAP_LINEAR` + `generateMipmap`（514² NPOT，WebGL2 允许）+ 有 `EXT_texture_filter_anisotropic` 就开最大；WRAP 两向 `CLAMP_TO_EDGE`。
- **片纹理 LRU**（照 `scene.js` 的 `tileTexes` 写）：键 `set/z/r/c`，上限 `TILE_TEX_LIMIT = 160`（≈ 1.34 MB / 片 → ≤ 215 MB 最坏）；逐出时跳过本帧在用的。上下文丢失清空。
- 网格缓冲：一次 `bufferData` 装分桶后的整份 `xy / uv`（float32）；键 = `planeKey + '/' + res + '/' + z + '/' + set`；复用判据照抄 `rmKey / rmBox`（钳过的视口落在上次规划框里就复用）。**瓦片到货不改键**：到货只换纹理与 `uUvOff / uUvScale`。
- 绘制：`for (bin of bins)`：`getTileOrParent(set, z, r, c, onTileReady)`；没有祖先则跳过该桶（留洞，海色垫在下面）；有则绑该片纹理（LRU 里没有就现传）、设 `uUvOff / uUvScale / uWin`、`drawArrays(TRIANGLES, first*3, count*3)`。桶数百余，一帧 < 1 ms。返回 painted > 0。
- 合成回 Canvas2D 与亮度 `ctx.filter` 照旧（`drawImageryGL` 末尾那几行）。
- `drawImagery` 投影分叉改为：

  ```js
  if (!PJ.identity) {
    if (imgSet) { if (drawImageryTilesGL()) return true; return blitReprojected(reprojectRasterTiles(), 1, imgBright, true) }
    if (!imgEl) return false
    if (drawImageryGL()) return true                                   // 整幅两行不动
    return blitReprojected(reprojectRaster(imgEl, null, true), 1, imgBright, true)
  }
  ```

  `exporting || compat` 仍恒走 CPU。

### 4.4 CPU 路（导出 / 无 WebGL2 / 上下文丢失）

- `reprojectRasterTiles()`：`rasterFrame` + `res`（口径与 `reprojectRaster` 同：屏幕分辨率、`RP_BUDGET` 封顶）→ `planRasterMesh(PJ, {…, S: WORLD})` → `binByTiles(M, z, imgSet)` → 逐桶 `getTileOrParent`，源坐标 `sx = G + (uOff + u'·uScale)·512`（祖先同式）→ `warpTri(g, tileImg, …)`。源图是 514²，`warpTri` 的「29 μs + 0.45 μs/MPix」里第二项归零 → **不用也不能用 `srcThumb`**（它假定源宽 = 360°）。缓存键 `rpKey` 加 `z + set + 到货代 gen`（CPU 路没有「只换纹理」这一说，到货要重烘）。
- `ensureImagery(opts)`：现在 `if (!imgOn || !imgSet) return` 后只处理等距圆柱的 `imageryPlan`；投影档要走同一套虚拟视图（`SV` 保存 / 恢复）算 `frame → plan → bins.tiles` 再 `loadTiles(imgSet, z, tiles)`。**导出前必须 await 到位**（同步渲染没有第二次机会 —— 与等距圆柱那条注释同一坑）。
- `bakeImagery`（矢量 PDF 的预合成一张）：`drawImagery()` 在 `exporting = true` 下自然走 CPU 瓦片路，不必另写；只要 `ensureImagery` 先把片等齐。
- 整幅 16K / 8K 的 CPU 路（`reprojectRaster(imgEl, null, true)`）**一行不动**（导出逐字节闸）。

- 验证台 `.imgharness/main.js`：`apply()` / `pxdiff()` 去掉 `imageryForFlat`；`window.flatSrcK` 改报 flat 的实际路径（`imgSet ? 'tiles/L' + z : imgEl 档`，从 `__rmStat` 取）。

### 4.6 与静态层调度的关系（不动调度层）

一切只发生在 `renderStaticLayers → drawBelowContent → drawImagery` 里：手势期靠快照 blit，静止后一次重建；到货走既有 `onTileReady → tilesDirty / rebuildAtRest`。`rebuildPolicy.js`、`viewCls`、cost 表都不改（瓦片与 16K 落同一 cls，代价由表自己学）。

### 4.7 不变式（改完自检，缺一不可）

1. 等距圆柱 2D（影像关 / 瓦片 / 16K / 8K）静止画面、导出 PNG / PDF：与改前**逐像素 / 逐字节相同**（`pxdiff`、`expdiff`）。
2. 五个投影档 × 16K / 8K：屏上 GPU 出图与导出与改前逐像素 / 逐字节相同（那两条路一行没动）。

4. 瓦片缺包（`resources/imagery` 不在）时投影档与等距圆柱一样：`drawImagery` 返回 false → 矢量底图，无报错、不黑屏，补上包下一帧自愈。

6. 品红垫底缺口率：五个投影 × 瓦片 × {全图, ×6, ×12} ≤ 0.2%、最长连续缺口 ≤ 5 CSS px（与方位等距 16K 现状同口径）。

## 7. 坑清单（这条链上踩过或读码看出来的）

1. **`getImageData` 禁用**：`imagery://` 来源上抛安全错并静默回退矢量底图；WebGL `texImage2D` 与 `drawImage` 没这问题（3D 与等距圆柱瓦片路都在用）。
2. **`srcThumb` 假定源宽 = 360°**（`want < sw` 那一句）：瓦片路不许调它。测试里 `const TH = srcThumb(S.img, sw, sh, res)` 那条锁的是整幅路，保留。
3. **列号取模只对 z ≥ 2 成立**（cols·span：L0 576°、L1 432°、L2 起 360°）：分桶按经度周期 p，不按列取模。
4. **L0–L2 边缘片有补边**（`tileClip` 的 fx / fy < 1）：uv 用全跨度归一，但只分给有效窗相交的片，着色器 discard 用 `uWin = (fx, fy)`。
5. **gutter 1 px**：纹理坐标 `(G + t·512)/N`，N = 514；写成 `/512` 会整体偏移一个纹素、片边一条线。3D 的 `tileTexture` 是对照。
6. **导出恒 CPU**：`drawImageryTilesGL` 头一行 `if (exporting || compat) return false`；`bakeImagery` 已钉 `exporting = true`。
7. **导出前 `ensureImagery` 必须 await**，且用导出视图（`SV` 保存 / 恢复那一套）算出来的片集 —— 屏上缓存里的片比导出要的粗好几级。
8. **到货回调不能在绘制里 await**、也不许每片触发重建：一律走 `onTileReady`（已带去抖 + 热态延后）。
9. **纹理 LRU 逐出要跳过在用的片**（3D 那条注释：一 break 就再也逐不动，显存只涨不跌）。
10. **上下文丢失**：`glRaster` 的 `webglcontextlost / restored` 已接 `invalidateStatic`；片纹理 LRU 与桶缓冲要在 `build()` 里一起清。
11. **`hasMesh` 键必须带 z 与 set**；到货**不**改键。
12. **planeKey 变**（换投影 / 切口 / 中心纬度 / 标准纬线）→ `rebuildPlane` 已清 `rmKey / rpKey`，桶缓冲跟着作废即可。
13. **测试对行尾敏感**（CRLF）：源码级断言用 `lf()` 归一。
14. **`pxdiff` 先预热一次**再比；基线副本要在动手前刷新。
15. **不写界面说明文字**（CLAUDE.md）；`imageryTitle` 不加字。
16. Electron 窗口驱动不了，像素级只在验证台 + 用户手测；报告里别写「已在 Electron 里实测」。
