# 任务书：2D 平面图整体流畅化（静态层真静态 + 影像 / 底图 GPU 化）

日期 2026-09-06。执行者：Opus。发起人：朴东旭。本任务书自带全部上下文，不依赖对话历史。
前一份任务书 `docs/2D分带填充GPU化任务书_2026-09-06.md`（已执行）只换了 GRD 分带填充那一层；本任务书治的是**它之外的一切**——底图、边界线、影像、地名——为什么在「10m 底图 + 影像 + 方位等距」下平移/缩放仍然卡。

## 0. 一句话目标

`src/viz/flatmap/flatCoverage.js` 的 2D 平面图，在「10m 底图 + 影像开 + 任一投影档（含方位等距）+ 国名/水域名开」的全图视角下，**平移每帧 ≤ 2 ms、缩放手势期间每帧 ≤ 2 ms**（静止后一次重建允许 ≤ 150 ms），投影档下影像**不再在平移/缩放时重烘**。3D、导出（PNG/PDF 逐字节一致）、GRD 填充的 GPU 路、STK 覆盖热力图、对星壳层覆盖一律不动。

## 1. 现象与根因（已实测，执行前不必重测；数字见 §1.2）

### 1.1 代码事实：所谓「静态层」每一帧平移/缩放都在整份重建

`draw()`（2121 行）的复合结构是：`blit below` → 夹层（晨昏线 / 环境场 / Polygon / 覆盖填充 / 等值线…）→ `blit above` → 顶层注记。below / above 两张离屏快照由 `renderStaticLayers()`（1929 行）重建，`staticValid` 为假时才重建。

但 **`onMove` 的 dragging 分支（2373 行）、`onWheel`（2159）、`setZoomT`（2168）、`panByPixels`（2645）、`setView`（2651）每次都 `invalidateStatic()`**。于是平移一个像素 = 把 10m 底图的 4448 个多边形填一遍 + 五类边界线 4953 条 Path2D 描一遍 + 235 个地名带套边写一遍 + （投影档）影像整份重投影一遍。「静态」只对时钟推进 / 覆盖场变化成立，对最常见的拖拽手势一次都不成立。

前一份任务书的 GPU 化只换了夹层里的 `drawField`，快照重建一行没碰——这就是「分带填充流畅了，底图还是卡」。

### 1.2 实测（`.imgharness`，真 `flatCoverage`，1280×720 CSS @ DPR 1.5 = 1920×1080 设备像素，10m 底图，国名 + 大洋 + 海域名开，无 GRD 层；每项 8～10 帧取中位数）

| 场景 | 平移一帧 | 备注 |

**归因试验**（等距圆柱 · 影像关 · 全图，总 157 ms；把 Canvas2D 原型方法打成空操作，只量光栅化归属）：

| 置空 | 一帧 | 结论 |
|---|---|---|
| — | 157 | |
| `stroke` | 23 | **五类边界线（含虚线两类）+ 经纬网的描边 ≈ 95～135 ms，是头号成本** |
| `fill` | 97 | 陆地填充 ≈ 20～25 ms |
| `fill` + `stroke` | 1.8 | 地名（235 × strokeText+fillText）+ 标记 + JS 合计 ≈ 2 ms —— **文字不是问题** |

**两条被否掉的便宜路**（都测过）：

- 把同样式同变换下的 4953 次 `stroke(Path2D)` 合成 9 次（`Path2D.addPath`）：**121 → 267 ms，更慢**。fill 合成 2 次：不变。成本在顶点 / 光栅化，不在调用次数——Canvas2D 侧的「批处理」没有出路。
- 瓦片 `HTMLImageElement` 预解码成 `ImageBitmap` 再画：99 → 83 ms，只省 16，不值得。

**规模**（`basemap-10m.json`）：面 4448 个 / 560 k 顶点；弧段 5124 条 / 484 k 点（最长 8 条各 8～17 k 点）。50m：1816 / 107 k；110m：290 / 10.6 k。全图视角 1920 px 铺 360° = 5.3 px/°，10m 顶点间距约 0.02° ≈ 0.1 px——**全图视角下 10m 的顶点密度是像素的百倍**，每帧都在光栅化屏幕上根本分辨不出的细节。

### 1.3 为什么 stroke 这么贵而且超线性

Skia 对带抗锯齿的细线（0.7 px）走的是逐段生成覆盖几何的路径渲染器，每帧按当前变换重做，且会先把路径裁到视口——所以放大后（大半顶点在视口外）便宜、全图视角（48 万点全在视口内）最贵；50m→10m 顶点 ×5、时间 ×37 是它的复杂度曲线。这不是我们代码里能调的参数。

### 1.4 影像重投影的缓存在全图视角下永远命不中（bug）

`reprojectRaster`（634 行）的复用判据（653 行）：

```
if (rpKey === key && rpBox && vx0 >= rpBox.x0 - 1e-6 && vx1 <= rpBox.x1 + 1e-6 && vy0 >= rpBox.y0 - 1e-6 && vy1 <= rpBox.y1 + 1e-6) return rpCanvas
```

`vx0..vy1` 是**未钳制**的视口世界坐标；全图视角（信箱留白）下 `vx0 < 0`、`vx1 > PJ.W`，而烘图矩形 `rpBox` 是钳到 `[0, W]×[0, H]` 之内的 → 条件恒假 → **每一帧平移都整份重烘**（实测 8/8）。放大到视口落进图幅内就正常（0/8）。修法：比较前把视口矩形钳到平面范围（与算 `bx0..by1` 同一套钳制）。

影像重烘本身的账（方位等距，全图 19.3 k 三角）：`warpTri` 逐三角 clip + drawImage 是 60 ms（srcThumb 命中）～960 ms（重缩一档）；**网格规划器本身只要 39 ms**（全图）/ 17 ms（放大）——把「贴图」这一步交给 GPU 之后，剩下的只有偶尔一次的规划。

### 1.5 未量化但代码可见的两处

- `drawAboveContent` 里一级 / 二级行政区界每帧走 `drawPolyline` → 投影档下 `drawPolylineProj`（1168 行）**每帧过一遍 d3 `geoPath`**（裁剪 + 自适应加密），没有像五类边界线那样烘成 Path2D。开 CHN adm2（4.5 万段）在投影档下会很重。验证台没有 IPC、拉不到行政区包，故未量；Phase 0 一并修。
- `drawBelowContent` 投影档海色的 `PJ.path({type:'Sphere'}, ctx)` 每次重建都过 d3：小，顺手缓存即可。

## 2. 结论：整个 2D 视图能不能用 WebGL2 优化

能，但**不该整个都上**。按每帧成本与 GPU 化难度分三档：

| 层 | 每帧成本（10m 全图） | 该怎么办 | 期次 |
|---|---|---|---|
| 静态层重建策略（平移/缩放即重建） | 100～260 ms 的**根因** | 平移只搬位图、缩放期缩位图、静止后重建 —— **不需要 GPU** | Phase 1 |
| 投影档影像重投影 | 60～960 ms/次，且全图视角每帧重烘 | 缓存判据修 bug（Phase 0）；纹理网格上 GPU，每帧只改 uniform | Phase 0 + 2 |
| 五类边界线 + 经纬网（描边） | 95～135 ms | GPU 线（挤出四边形 + 片元 AA + 虚线）—— 最难的一块，**门控** | Phase 3 |
| 陆地填充 | 20～25 ms | GPU 模板 evenodd（与 `fill('evenodd')` 同语义，不用 earcut） | Phase 3 |
| 地名 / 数值 / 标记文字 | ≈ 0.6 ms | **留在 Canvas2D**。GPU 文字 = 字形图集，得不偿失 | 不做 |
| 标记符号 / 地球站 / 卫星图标 / 航迹 | < 1 ms | 留在 Canvas2D | 不做 |
| 等距圆柱瓦片影像 | 几十次 drawImage，Phase 1 后每帧 0 次 | 留在 Canvas2D | 不做 |
| 导出 PNG/PDF | — | 恒走 Canvas2D compat（与 glField 同一口径） | 不动 |

Phase 1 做完，平移就已经是 0.2 ms；Phase 3 买的是「10m 全图视角下缩放手势每一档都清晰」「LEO 星下点跟随（每 250 ms 重建平面）不顿」「拖动调整中心可用 10m 而非 110m 骨架」。它是最重、最容易在视觉上翻车的一期，**先做 0–2，量完再决定 3**（§9）。

## 4. 设计

### 4.0 Phase 0 —— 三处即修（半天）

1. **影像重烘缓存判据**（653 行）：比较前把 `vx0/vx1/vy0/vy1` 钳到 `[0, PJ.W]×[0, PJ.H]`（与 `bx0..by1` 同一套钳制），全图视角平移不再重烘。验收：方位等距 + 16K 全图视角 8 次平移 0 次重烘（`globalThis.__bakeStat` 对象身份不变）。
2. **行政区界烘成 Path2D**：投影档下 `prov.borders / city.borders` 与五类线同策略——按平面烘一次（`bakeBorders` 的投影档分支就是范本：`projRec(true)` 一次烘完、按子路径拆开、记 `lo/hi` 供视口裁剪），每帧只 `stroke(path)`；`setProvinces / setCities / rebuildPlane` 作废缓存。等距圆柱那条路本就是屏幕坐标直连，可一并烘成世界度 Path2D，也可不动。
3. `drawBelowContent` 投影档海色 Sphere 与 `drawSphereOutline` 共用同一条缓存的 `sphPath`（后者已缓存）。

### 4.1 Phase 1 —— 静态层真静态（核心，约 1～2 天）

目标：平移 = 搬位图；缩放手势期 = 缩位图；只在「手势静止」「拖出快照覆盖范围」「内容真变了」时重建。

- **快照带余量（overscan）**：两张快照按 `(1 + 2·m)` 倍视口尺寸建（设备像素），`m` 建议 0.25～0.35，且**钳到世界矩形**（全图视角下世界已在画布内，余量全是空的，别白留内存）。记录烘制时的 `snapK = k()`、`snapTx/snapTy`（快照左上角对应的 CSS 坐标）。内存：1920×1080 × 2.25 × 4 B × 2 张 ≈ 37 MB，可接受；`resizeNow` 同步改尺寸。
- **虚拟视口烘制**：重建时临时把 `cw/ch/tx/ty` 换成余量框（与 `exportRender` / `ensureImagery` 的 `SV` 保存-恢复同一手法），调用现有 `drawBelowContent / drawAboveContent` 后恢复。所有按 `cw/ch/tx/ty` 做视口裁剪的地方（陆地 / 边界线 / 地名 / 瓦片排布 / 影像烘图框）**自动**对余量框生效，一处都不用改。
- **`draw()` 的判定**：
  - `k() === snapK` 且视口落在快照覆盖内 → `drawImage(snapshot, dx, dy)`，`dx = (tx − snapTx)·dpr`（两张各一次，与现在的 blit 同位置）；
  - `k() === snapK` 但拖出覆盖 → 同步重建（每拖过约半个视口才发生一次）；
  - `k() !== snapK`（缩放中）→ 用 `drawImage` 按 `k()/snapK` 缩放贴上（缩放锚点按世界坐标换算），并用一个短去抖（80～120 ms 无新缩放事件）触发重建；**若上一次重建耗时 < 8 ms（放大视角 / 50m）则直接同步重建**，别为便宜的视角引入模糊帧。缩放期间地名 / 标记 / 线宽跟着位图一起缩，静止后归位——每一款 slippy map 都这样，可接受，但要在报告里明说。
  - 其余所有 `invalidateStatic()` 调用点（换地名档 / 边界样式 / 瓦片到货 / 换平面 / 视角广播…）语义不变 = 整份作废。
- **平移 / 缩放不再调 `invalidateStatic()`**，改成「记视口变了」；`rotLive`（拖动调整）仍走整份重建（110m 骨架 24 ms，现状可用）。
- `reprojectRaster` 的 `RP_PAD` 与快照余量叠加会多烘一圈：Phase 2 之后它不存在；Phase 1 期间把 `RP_PAD` 降到 0～0.1 即可。
- 加开发期计数器 `globalThis.__staticStat = { mode: 'blit'|'scaled'|'rebuild', rebuildMs, reason }`（与 `__fillStat` / `__bakeStat` 同款，用户手测时在控制台读）。
- **一帧一个时刻**的铁律只约束数据层（覆盖场 / 晨昏线 / 聚焦星几何，它们在夹层，每帧照画），底图快照是纯外观，延后重建不违反它。

### 4.2 Phase 2 —— 投影档影像改 GPU 纹理网格（约 1～2 天）

现状的账：贴图（`warpTri` 逐三角 clip + drawImage 整张源图）60～960 ms，规划器 17～39 ms。GPU 化之后只剩规划器，而且只在换平面 / 换分辨率档时跑一次；每帧只改 uniform。

- 新模块 `src/viz/flatmap/glRaster.js`（或与 `glField.js` 合成一个共享上下文的 `gl2d.js`——由你定，判据：两个上下文各自独立最省事；合并则 `antialias` 要统一为 true，见 4.3）。程序：`aPlane(vec2)` + `aUV(vec2)`，顶点 `平面 → CSS px → clip` 与 glField 同一式子（`uK/uTx/uTy/uDpr/uW/uH`），片元 `texture(uTex, vUV) * uBright`。
- **网格来自现有规划器，不另写一套**：把 `reprojectRaster` 里的两个循环（正向 `lonBreaks + planCells`；反向 `planBlockInv + cellCornersInv`）抽成生成器 `planRasterMesh(PJ, box, res, S) → { plane: Float32Array, uv: Float32Array, idx }`，CPU 路（导出 / 无 WebGL2 / 环境场栅格）继续拿它喂 `warpTri`，GPU 路拿它建缓冲。这样两条路的几何逐字相同，验收才有据。
- 反向网格档（方位等距）跨 ±180 接缝「画两遍」那条（projection 记忆里的坑 7）在 GPU 上**不需要**：整幅世界图正好 360° 宽，纹理 S 方向设 `gl.REPEAT`，UV 直接越界即可（局部 bbox 的环境场栅格仍要 `CLAMP_TO_EDGE`，别混）。`TRI_PAD` 边法线外扩那套抗缝技巧也不需要（共享顶点天然水密）。
- **纹理**：沿用 `srcThumb` 的分档（2048 / 4096 / 8192；16K 原图 512 MB VRAM，2D 是与 3D 独立的上下文、显存要再算一份，**不要**直接传 16K），`generateMipmap`，`smooth` → `LINEAR_MIPMAP_LINEAR` / `NEAREST`。3D 已把同一张图和同一批瓦片当纹理用（`scene.setImagery / updateImageryTiles`），`imagery://` 与 `file://` 来源上传 WebGL 纹理没有跨源问题——只有 `getImageData` 才有，不要走它。
- **网格重建时机**：换平面（`rebuildPlane`）或 `res` 跨 2 的幂档（网格只需「不比屏幕粗」，GPU 不在乎多画三角）；平移 / 缩放期间一律不重建。规划 17～39 ms 一次，可接受；想再省可按档缓存网格。
- **合成**：影像在最底层，`drawBelowContent` 里 `drawImagery()` 投影档分支改为「GL 画完 → `ctx.drawImage(glCanvas)` 一次」（整幅或世界矩形包围盒，与 `drawFieldGL` 同一套）。等距圆柱瓦片路不动。
- 导出（`compat` / `rasterOut` / `bakeImagery`）与无 WebGL2 一律走 CPU 路：`exporting || compat || !gl.available()` → `warpTri`，判据与 `fieldBackend` 同款。

### 4.3 Phase 3（门控，见 §9）—— 底图线 / 面上 GPU

只在 Phase 1–2 之后按 §9 的判据仍不达标时做。这是本任务书里唯一有视觉翻车风险的一期：用户对边界线的明度 / 粗细 / 虚线周期极其在意（见 `../geo/borderStyle.js` 与 3D 侧的同名常量），像素级比对台是硬门槛。

- **先查成熟实现再动手**（平台惯例）：mapbox-gl-js 的 `line_bucket` + `line.vertex.glsl` / `line_sdf.fragment.glsl`（挤出 + 法线 + 累计长度做虚线）、rreusser/regl-gpu-lines（joins / caps 的几何做法）、deck.gl `PathLayer`。不要凭感觉手搓 join。
- **线**：每条折线按平面坐标挤成四边形带，顶点属性 `pos(vec2) / normal(vec2) / side(±1) / len(累计平面长度)`；顶点着色器按 `uWidthPx / (uK·uDpr)` 在平面单位里挤出（线宽恒定屏幕像素）；片元用到中线距离 + `fwidth` 做 AA；虚线 `mod(len·uK·uDpr + phase, period)` 对照 `DASH_PX` 图案（uniform，最多 4 段）；圆角 join / cap 用扇形补片或 SDF 圆。五类线 + 经纬网 + 行政区各一组缓冲，按 `BORDER_DRAW` 顺序画，`admFade` 走 alpha uniform，等距圆柱 ±360 走 `uOff`。
- **面**：模板 evenodd（stencil-then-cover）：每个颜色组先以 `INVERT` 把各环的三角扇写进模板（关颜色写入），再画包围矩形按模板覆盖颜色，清模板进下一组。与 Canvas2D `fill('evenodd')` 逐语义相同，南极收口环 / 洞 / 退化环都天然正确（3D 的 earcut 在 50m 南极上翻过车，这里不复现）。需要 `stencil: true` + `antialias: true`（MSAA 给面的边缘 AA）。
- 落地后 below / above 快照里只剩影像 + 地名 + 标记，可考虑把线 / 面改成每帧直画（1～2 ms），快照只留文字层；也可仍进快照——按实测定。
- 验收：与 `.fillharness/gl` 同款的逐像素比对台，差异分「线宽内 AA 差 / 端点与拐角 / 其余 = 0」三类；**截图给用户过目再合并**。

### 4.4 一项要用户拍板的选项：按屏幕密度自动选底图档

全图视角 5.3 px/° 时 10m（≈ 0.02° 一个顶点）与 50m（≈ 0.1°）在屏上不可分辨，而重建成本 120 ms vs 3 ms。GIS 通行做法是按比例尺综合：`k()·dpr < 约 20 px/°` 用 50m，之后才用 10m（阈值按「50m 顶点间距在屏上超过 2 px」定，实测校准）。它把「10m 全图视角缩放一次重建 120～160 ms」直接消掉，Phase 3 的必要性会再降一档。

顾虑：50m 是 363 个单元、10m 是 370 个，跨档瞬间小岛 / 小单元的形状会有肉眼可察的一跳；110m 没有争议面图层，**永远不许自动选到**。这是显示口径的改变，**不要擅自做**：Phase 1 报告里附上两档在全图视角的截图对比，由用户决定；若做，落成画质档「自定义」里一行拨杆（无说明文字，CLAUDE.md）。

## 7. 坑清单（都踩过）

1. **验证台的 rAF**：Browser 面板藏起来时原生 rAF 完全停摆；`.imgharness/main.js` 已用 MessageChannel 顶替，别改回 setTimeout（后台页被钳到 1/s）。

### 10.3 Phase 1

按 §4.1 落地，四处与任务书写法不同（都是实测逼出来的）：

1. **快照有效的判据是「盖住【世界矩形 ∩ 视口】」，不是「盖住视口」**。世界之外快照上本就是背景（below）与透明（above），与现画一遍逐字相同。这一条让**全图视角（信箱留白）平移多远都命中**，且此时余量可以是 0 —— 而全图视角正是本次要治的那一档。
2. **余量按世界矩形是否真伸出视口给，且是【设备像素的整数】**（量化到 64）。整数是硬要求：① 瓦片影像的片边按 `round(css×dpr)` 取整，余量在 CSS 上不是整像素就会挪掉取整相位、缝的位置全变；② 合成时的位移才落得到整设备像素上，不触发位图重采样。比例取 **0.18**（不是 §4.1 建议的 0.25～0.35）——上限必须钉在 `RP_PAD`(0.20) 之下，见第 4 条。
3. **余量为 0 时原样走老路**（渲到主画布再拷到离屏缓冲），余量不为 0 才直接渲到离屏缓冲。前者是全图视角，于是与改造前逐字节同一条指令流，逐像素相同由构造保证。
4. **`reprojectRaster` 用【真视口】而不是虚拟视口**（`realView`）。烘图框一变，重采样相位就跟着变，静止画面就不再逐像素相同；快照那圈余量由 `RP_PAD` 兜住（故 OVER < RP_PAD）。**`RP_PAD` 没有按 §4.1 降到 0～0.1** —— 降了就是挪烘图框，同样破逐像素。
5. 另外：1:1 那条 blit **只搬落进画布的那一块**（九参 drawImage，坐标全整数、源目同尺寸，仍是 1:1 快路）。整张搬两遍是 7.7 MPix 的白拷贝，实测把放大视角的平移从 1.1 ms 拖到 6.5 ms。位移正好为零时仍走三参 —— 与改造前同一条调用。
6. 取整的残差（DPR 1.5 下奇数像素的拖动会剩 0.5 设备像素）与缩位图一样，交给 `scheduleRebuild()` 在手势停下 110 ms 后补一次精确重建 → **静止时画面永远是精确重建出来的那一张**。
