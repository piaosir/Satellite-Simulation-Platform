# 版本说明 · 3GPP NR-NTN / NB-IoT NTN 深度审查修正（2026-09-06）

> 对应任务书 `docs/NTN深度审查修正任务书_2026-09-06.md`。落在 v1.4.3 之后的两个提交上：
> 一期 `9a1f687`、二期 `cb9213f`。
> 本次只动 3GPP NTN 那条链：**DVB 各体制与「自定义」的计算逐位不变**（`accuracy` / `linkChain`

## 1 这次改了什么

### 一期：界面配得出标准里没有的载波

| 项 | 根因 | 口径 |
|---|---|---|
| NPUSCH 单音表 / 多音表与「子载波数」解耦 | 「子载波数」下拉对任何 NB-IoT 上行标准都给 `[1,3,6,12]`，而「表里的行号是 I_MCS 还是 I_TBS」按当前子载波数判 | 子载波数由标准锁定（`phy.st`）：单音表恒 1 个子载波、多音表只有 3/6/12 且恒 15 kHz。选单音表再改成 12 音，原先门限仍取单音那一列（高 1.6 dB@I_TBS 0 … 3.8 dB@I_TBS 10），且 π/2-BPSK 被套到多子载波上（TS 36.213 §16.5.1.2 规定 N_sc^RU > 1 时恒 QPSK），I_MCS 1 又被当 I_TBS 1（应为 2） |
| 变换预编码表允许选「下行」 | 面板的方向下拉对所有 NR 表可用 | Table 6.1.4.1-1/-2 只用于 transform precoding 使能的 PUSCH（TS 38.214 §6.1.4.1），归一化时强制上行、面板禁用该下拉 |
| 重复次数不校验值域 | 填 3 或 5000 都照算，门限按 10·lg N 白降下来 | NB-IoT 判枚举并列出合法值（NPDSCH 16 档到 2048、NPUSCH 8 档到 128）；NR 只判上限（PDSCH 16 / PUSCH 32），不卡枚举 |
| NR 换方向不复位分配 | 下行 25 PRB / 5 MHz 切到上行原样留着，把一个终端的分配报成整载波（转发器带宽占用比虚高 27 倍） | 换方向按该方向缺省重铺信道带宽 / PRB 数 / 符号数 |

### 二期：表数据停在旧版本、显示值是编出来的

| 项 | 根因 | 口径 |
|---|---|---|
| 信道带宽档不按逐频段表 | 可选档取自 N_RB 表（Table 5.3.2-1）而非逐频段表（Table 5.3.5-1）。前者只说「这个带宽在这个子载波间隔下是多少 PRB」，**哪个频段允许哪几档是另一张表** | 新增 `NTN_BANDS`（TS 38.101-5 V19.5.0 全量 14 个频段），`phy.band` 参与校验；面板加「NTN 频段」下拉 |
| 60 kHz 一张表混了两个 FR | FR1 的 60 kHz / 50 MHz 是 65 RB、FR2 是 66 RB —— 同一个键两个值 | 拆成 `NR_RB_FR1` / `NR_RB_FR2`；FR 归属由**频段**定，不再用 `scs ≥ 120` 猜（后者让 n510–n512 的 60 kHz 拿到 FR1 的开销系数 0.14/0.08 而不是 0.18/0.10） |
| NB-IoT TBS 表停在 Rel-13 | 是 v13.2.0 的截断表（32 个空格 + 缺 I_TBS 13），而 IoT-NTN 的商用模组几乎全是 Cat-NB2 | 换成 TS 36.213 V17.4.0 / V18.3.0 的 14 行 × 8 列全表；三张 MODCOD 表各补 I_TBS 13 行 |
| 「FEC 码率」列是编出来的数 | 写成 `TBS/264`，而 264 =（14−3）×12×2 对哪一张表都不是分母 | 按 TS 36.211 的结构算分母：NPDSCH 304 bit（带内 208）、NPUSCH 多音 288 bit、单音 96×Qm bit；分子含 24 bit CRC。级联表对 NB 行由引擎按当前 I_SF/I_RU 与部署模式现算 |
| 3GPP 行印着「误码率 1×10⁻⁷」 | 3GPP 门限按 BLER 10% 首传给，那个值却来自 DVB 的表单缺省 | 3GPP 行改出「目标 BLER」（一个数，不是文字判定），DVB 行一位不变 |
| 新增「部署模式」 | 带内部署的 NPDSCH 前 3 个符号让给 LTE 控制区并被 CRS 打孔 | `phy.opMode`（独立 / 保护带 / 带内）：带内时编码比特数 304 → 208、I_TBS 只到 10（NPUSCH 不受限） |
| 出处写错 / 写漏 | —— | IoT-NTN **有**独立的 UE 射频分册：TS 36.102（终端）与 TS 36.108（SAN），原「36.101 不分册、未见独立分册」那条诚实边界已消解；FR2-NTN 的 N_RB 表已核到 Table 5.3.2-2 原文，「按 38.101-2 同值收」那条一并删；报告参考文献与《官方数据与算法来源》台账同步 |

## 2 老配置怎么迁移：一个数都不改

新增的四个字段全部按「老配置没有它 → 归一化给一个不改变任何行为的缺省」处理，
**只有用户重新选一次 MODCOD 才对齐到本版内置骨架** —— 与门限那一列同一个不静默口径。

| 字段 | 老配置没有它时 | 重新选 MODCOD 后 |
|---|---|---|
| `phy.band` | `''` = 不指定 → 按该 FR 所有频段的**并集**放行，逐位照旧算得通 | 铺内置骨架的 `n256`（S 频段，TR 38.821 基线） |
| `phy.opMode` | `'standalone'`（NTN 的典型形态，TS 36.102 §5.4B.1 的 200 kHz 独立栅格）—— 编码比特数 304 bit，与改动前的显示口径一致 | 同左 |
| `phy.blerTarget` | `0.1` —— 3GPP 八张表本来就是 BLER 10% 首传，回显 10% 即实情 | 跟 `meta.bler` 走 |
| `phy.st` | `null` = 不锁 → 行号按当前子载波数判，与改动前逐位一致 | 跟该标准走（NPDSCH `null` / 多音 `false` / 单音 `true`） |

另外两处刻意保守：

- **信道带宽反查跳过「本版可选」档**。Rel-19 给 L/S 各频段新加了 3 MHz（NOTE 2 可选）。若参与反查，
  1 PRB 的下行会从 5 MHz 改报成 3 MHz —— 那是静默换数。要用可选档，在下拉里显式选。
- **老式 esno 行的带宽判据回到 Rel-17 的 L/S 四档**（5/10/15/20 MHz），不再派生自频段清单。
  那些配置成型时平台里只有 n254/n255/n256；把 Rel-19 的 Ku 100 MHz、FR2 400 MHz 并进来，
  只会让「填了 36 MHz」这种明显配不出的带宽落到 50 MHz 档上。

### 一处顺带修的：MODCOD 下拉的选中态

三张 NB-IoT 表的行标签从 `I_TBS 0  QPSK 16/264` 改成 `I_TBS 0 · QPSK · TBS 16`（不再印那个假分数）。
面板原先只按 `modcodLabel` 反查选中行，改名后老配置打开时下拉会整个显示成未选中。
故 `modcodSel` 加了一层行号兜底：名字对不上就退回 `modcodIndex`（内置表只增不改序，行号可靠）。
`form.fec` / `form.ebno` 等表单值本来就原样保留，**任何计算结果不受影响**。

## 3 与任务书原文不符的三处（已按原文落地，请复核）

1. **PUSCH 重复上限不是 `numberOfRepetitionsExt-r17` 到 n32**。核 TS 38.331 V17.5.0：
   该 IE 是 `{n1,n2,n3,n4,n7,n8,n12,n16}`，到 **16**；到 n32 的是同一个扩展组里的
   `numberOfSlotsTBoMS-r17`（一个传输块跨多个时隙，链路预算上与重复同效）。
   上限仍按 32 收（不把 Rel-17 覆盖增强那一档挡在外面），但注释里的出处已改正。
2. **Kodheli 表 3 的 I_TBS 13 不是「作者取了别的 TBS」**。用 Rel-14 全表按「每档取最大吞吐」反推，
   1032/4/180 kHz = 1.4333 与原文印的数**完全吻合**。28 格里 25 格吻合到 1e-4；
   不吻合的是 I_TBS 3 / 4（两列各差 ±0.002，作者自己那一档的取整）与 **I_TBS 12 的下行**：
   表里印 1.3889 = 1000/4，而 1000 是 **NPUSCH** 表那一格，NPDSCH 是 904（→ 1.2667）。
   即他们的下行 SE 抄了上行的数 —— 这一条反过来证明本平台的下行表没抄错。该交叉验证已写成断言。
3. **单子载波的 I_TBS 只到 10**（顺手挖出来的，任务书未列）。Table 16.5.1.2-1 的单音行只有
   I_MCS 0–10，映射出来的 I_TBS 就是 {0…10}，11–13 那三档单音根本取不到。
   原先放任它算，新加的「有效码率」会算出 1.04~1.33 这种 >1 的数。现已报错。

## 4 待拍板：ITU PFD 限值对窄载波偏严（P3-8，**非 NTN 行**）

`linkCalculator.js` / `linkCalculatorNGSO.js` / 再生式三处同款：

```
ituPfdLimitPerM2 = limit_4kHz + 10·lg(B / 4)
```

限值定义在参考带宽 B_ref（4 kHz 或 1 MHz）内。载波带宽 B < B_ref 时全部功率都落在一个参考带内，
允许的总 PFD 就是 `limit_ref`，不应再减。正确式：

```
ituPfdLimitPerM2 = limit_ref + 10·lg(max(B, B_ref) / B_ref)
```

对 NTN 行是恒等变换（下行占用带宽 ≥ 180 kHz，Ka 的 FR2-NTN ≥ 50 MHz），
**只影响 DVB 的窄载波**——例：Ka 频段 100 kHz 的 SCPC，现值偏严 10 dB。
碰到「DVB 一位不变」这条红线，**本次未改**，请拍板后另立任务书。

## 5 下一步（P3-11，本次不做，各自另立任务书）

1. **HARQ / RTT 可调度占空比**。现在的「信息速率」是物理层瞬时速率（每时隙都调度）。
   GEO 往返 541.46 ms（TR 36.763 Table 6.1-1），NR 32 个 HARQ 进程 × 1 ms 时隙只覆盖 6% 的 RTT，
   不关 HARQ 反馈时实际吞吐只有峰值的 6%；NB-IoT Cat-NB1 1 个进程、NB2 2 个，且
   NPDCCH→NPDSCH ≥ 5 子帧、NPDSCH→HARQ-ACK ≥ 13 子帧、锚定载波只有约 8/10 子帧可用。
   建议加一列**可选**出参「平均可调度速率」，默认不勾，假设写进 `title`。
2. **TR 38.821 / TR 36.763 的参考终端与卫星预置**：手持 23 dBm / 0 dBi / NF 7 dB / G/T −31.6 dB/K，
   VSAT 33 dBm / Tx 43.2 dBi / Rx 39.7 dBi / NF 1.2 dB / G/T 15.9 dB/K，卫星 Set-1…Set-5。
3. **eMTC-NTN（Cat-M1）**：IoT-NTN 的另一半，1.4 MHz / 6 PRB（TS 36.102 Table 5.3A-1），
   TBS 走 TS 36.213 §7.1.7.2.1 的 LTE 表。
4. **NB-IoT 16QAM（Rel-17）**：I_TBS 14–21（独立部署），DL TBS 最大 4968。NTN 链路预算里极少用到。
