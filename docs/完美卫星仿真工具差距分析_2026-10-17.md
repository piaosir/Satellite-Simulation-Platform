# 距「完美的卫星仿真工具」还差什么 —— 全面差距分析（2026-10-17）

> 只读分析，没有改任何代码。基线：v1.5.3 + 当日工作树（含其他会话尚未提交的改动）。
> 方法：八路并行——轨道与时空基准（A）、覆盖与可见性（B）、射频与传播（C）、干扰与 ITU 规则（D）、天线波束与载荷（E）、仿真框架（F）、工程底座与商用质量（G）、业务链与市场（H）。每路以行业标杆（STK、SATSOFT、Visualyse、GMAT / Orekit、ITU BR 软件、SatMaster、MATLAB）与现行标准为尺子，量级尽量用脚本直接跑仓库生产代码得出；C 路下载了 ITU 官方验证算例 ValEx Rev 8.3.0 逐例对拍。所有 P0 结论由主会话逐条回到代码核实，正文标「已核」。行号会随代码漂移，以函数名为准。
> 「最佳实现」口径：按行业标杆一步到位，不写「一期先做简化版」。用户亲自回退或否决过的，不当新建议提出，统一放在 §12「需你重新考虑」。
> 与既有文档的关系：《现有软件体检》《前端设计深度审查》《交互方式深度调研》《性能深度分析》查的是 BUG、交互、前端、性能；本文查的是「能力与保真度」，两者不重复。§13 把那些文档里没结清的账汇总到一处。

## 0 结论

### 0.1 总体判断

**在「GEO 卫星通信工程」这条主线上，平台已经是专业级，并有多处达到或超过行业标杆：**
- **日凌预报**：68 站 × 1094 天与运行原件对拍，时长偏差均值 +0.05 min。竞品 AsiaSat / APSTAR 自称误差 5–10 min。
- **P.618 雨衰全链**：对 ITU 官方 ValEx 8.3.0 的 64 例，偏差 ≤ 0.01 dB；XPD 56 例差 5e-14 dB。
- **PFD / EIRP 掩模**：通过 XSD v4 校验，并在 ITU Mask Viewer 上验证过。
- **NGSO 时变 C/I 的统计层**：多历元块 bootstrap、in-line 细化。
- **天线与覆盖**：GRD 等值线做到「线 = 表」；赋形是严格 minimax（SLP + 内点 LP）；相控阵 PAM 与 SATSOFT §6.5 逐字段对齐。
- **星历与报告**：星历格式字节级回环；交付级报告用一个模型渲染出三种文件。
- **规划闭环**：频率计划 → 逐转发器容量 → SLA。六家国际标杆工具的公开资料里都没有这一段。

**距「完美」差在五层，按紧迫度排：**
1. **会算错的硬伤**：本次新查出 18 条，已逐条核实（§0.3）。集中在四处：雨以外的传播链、ITU 干扰规则、HTS 方向图、事件检测。量级从 0.3 dB 到 21 dB，其中几条会让结论反向。
2. **可信度证据**：没有 ITU 官方算例级的 V&V 体系。现行《ITU-R 计算准确性校验报告 v1.1.2》每个模型只验了 1 个点，其中两条结论在全量官方算例下不成立；交付报告的参考文献还列了引擎没实现的方法。对专业工具来说，证据和计算本身同等重要。
3. **商用底座的一票否决项**：更新无签名却全员静默安装；三个 GitHub 仓库公开且声明 MIT；云凭证随包分发，share/* 可匿名读取；中国边界数据的来源许可写明「仅供学习和交流使用」，出图也没有审图号；只能在线激活，内网环境装得上却激活不了；没有手册与 EULA；Electron 31 已停更 21 个月。
4. **仿真框架骨架**：缺统一对象模型、工程文件、事件库、数据提供器、自动化 API / 命令行、参数研究、计算作业层。这是「13 个计算器」与「一个仿真工具」的分界，也是后面多数领域能力的地基。
5. **领域能力缺口**：
   - GEO 飞行动力学：位保、共位、倾斜运行；
   - GSO 协调链：AP8 / AP5 / SRS；
   - 地面业务干扰与站址评估；
   - HTS 容量与指向误差；
   - 约束目录与选星切换、移动终端姿态；
   - 电离层、移动信道、ACM 统计、载荷非线性、不确定度；
   - NGSO 动态波束与载荷资源。

**另有一笔不属于「差距」、但必须先清的账**：约 40 项功能和 6 批修复（合计 100 多条）处在「已修、未提交、未实测」状态（§13.1）。新的大块工作开工前，应先把它们实测收口、分批提交、发一版。

### 0.5 框架骨架：从「13 个计算器」到「一个仿真工具」

平台缺的不是某个单项功能，而是 STK 那根骨架。下面七件互相依赖，宜按这个顺序做：
1. **统一对象模型 + 工作区库**（F-01 + G-09）。同一棵卫星天线树今天在 localStorage 里有 5 份，身份键有 6 套。
2. **工程文件**（F-02，交互调研 C7 待拍板）。
3. **计算作业层**（F-09）。现在二维扫描在主进程同步跑，8 核只用 1 核。
4. **分析时段与事件库 + 时间线视图**（F-04）。
5. **数据提供器 + 报表 / 图表管理器 + 条带图**（F-06 / F-05）。
6. **事务式撤销**（F-03）。
7. **平台 API / 命令行 / Python 客户端**（F-07）与**参数研究**（F-08）。

这根骨架也是 HTS 容量（E-04）、时变链路（C-09）、不确定度（C-14）、选星（B-04）、星座运管 S1–S7 的地基。不先做，每个新模块都要再复制一套存储、时窗、导出和进度条。

### A-01 GSO 链路与干扰把卫星当定点：保持盒与倾斜运行对跟踪、指向损耗、时延、多普勒的影响都没算 〔P0（倾斜运行星 / 固定天线）· M–L〕
- **现状（已核）**：GSO 引擎仰角只用轨位经度、按球地球公式（linkCalculator.js:459-465，0.15127 = R⊕ / r_GEO），斜距 :494-500，时延 :1238；无倾角 / 偏心率 / 保持盒输入，无指向损耗项（`calculatePointingLoss` 早已随「精细化损耗参数」删除，:1400）；C/I 的 GEO 邻星按标称轨位（interference/geometry.js:14-17）。
- **量级**（A 路 exp5，北京看 110.5°E，高斯主瓣近似）：保持盒（i = 0.05°、e = 3e-4）视线偏 0.055° → 9 m Ka / 13 m Ku 固定指向损耗 2.7–2.8 dB；i = 1° 视线偏 1.11°、斜距日变 161 km（0.54 ms）、12 GHz 多普勒 ±236 Hz，1.2 m Ku 固定天线损耗 7.5 dB，2.4 m 以上直接出主瓣；i = 3° 视线偏 3.35°、斜距日变 479 km、多普勒 ±701 Hz。**快照里中星 2A / 4A / 9 / 2C 倾角 1.76 / 1.01 / 0.97 / 0.58°**（exp9）——这些星的客户链路预算现在静默按定点算。中星 2A 与中星 2E、中星 11 同在约 98°E，C/I 拓扑角每天变化约 ±2°，静态 C/I 体现不出。
- **最佳实现**：`packages/core/utils/geoTrack.js`：卫星 ECEF 序列取自 orbitPos（TLE / 叠加星历 / A-02 预报 / A-03 传播），或「标称轨位 + ±Δλ / ±Δφ + e」合成；逐站算日内方位 / 仰角 / 距离与相对日平均指向的偏离；损耗优先用 GRD / 实测方向图，缺省高斯主瓣；跟踪方式（固定 / 步进 / 程控 / 单脉冲）给残差模型；输出指向损耗（最大值与时间百分位）、最低仰角、时延范围、多普勒范围数值列接入 GSO 链路预算（缺省仍「定点」，守回归）；C/I 的 GSO 邻星改按各自星历逐时刻算拓扑角。
- **验证**：本机 STK 出 AER 报表对拍；Soop 的 8 字幅度闭式；exp5 数值作回归。

### A-03 只有 SGP4 / SDP4：无数值 / 半解析传播与力模型 〔P1 · XL〕
- **现状**：传播类型只有 SGP4 与插值星历（orbitPos.js:65-86）；grep 积分器 / 力模型关键词无结果。STK 式加星任务书 §14 曾把「HPOP 等数值积分」列为不做（理由：外部星历导入即承接）——本条按「最佳实现」口径重提传播器（不是精密定轨）。
- **为什么 SGP4 不够（GEO）**：SDP4 在 i < 3° 时把日月长期节点率清零（vendor/satellite.js:576-591，**已核**，这是 Vallado 原码本身的特性），倾角矢量一年漂移量取决于历元 RAAN：i = 0.05°、RAAN 0° / 180° 时 SDP4 0.06 °/年 vs 独立数值积分（J2 + 日月）0.92–0.93 °/年（约 15 倍）；4° 时两者一致（说明积分器可靠）。SGP4 完全不含光压（上面 ±0.077° 偏心率年圆整块缺失）。精密星历不外推，时段外回落编目 TLE，而机动后 TLE 在 2 / 5 / 9 天偏 27 / 68 / 124 km（124 km 在 37000 km 处 = 0.19°，大于 13 m Ku 站 θ3dB）。运管任务书的 cam.js、decay.js 也没有可依托的传播器（A-14）。
- **最佳实现**：`packages/core/utils/prop/`：`numProp.js`（DOP853 + 稠密输出供事件求根，可选 Gauss-Jackson）；`forces/`（EGM2008：GEO 缺省 8×8、LEO 21×21、最高 70×70；日月缺省平台解析历表、可选 DE440 子集；光压复用 eclipseFactor；阻力 NRLMSISE-00，空间天气取 CelesTrak SW-All.csv 走 solarFlux.js 同款四级链路；固体潮按 IERS 2010）；`dsst.js`（半解析长期预报）；产出 ephem 表直接进 orbitPos，新增传播类型 'num'，Worker 里算；初值取 OEM / .e / .eph 任一时刻、OPM 或 TLE 历元。
- **验证**：GMAT / STK HPOP 同力模型 7 天对拍；卫通 .eph 无机动段外推对拍。
- **许可**：EGM2008、DE440、NRLMSISE-00 移植版许可未核实；Python 版 nrlmsise00 是 GPLv2，不能进包。

### B-01 过境与覆盖事件检测是定步采样：短过境漏检，重访 / 中断类指标系统性偏差 〔P0 · L〕
- **现状（已核）**：过境粗扫写死 90 s，只在相邻两粗扫点间跨门限才二分精炼；代码注释自承「完整落在两个粗采样格之间的极短过境会被漏掉」（visibility.js:215）。覆盖核按采样计数（缺省 60 s）：访问次数 = 采样上升沿数，最大重访 = 最长未覆盖采样串 × 步长。主进程 `solveAccessWindows` 用 `findWindows`（步长 min(P/200, 60 s)），C/I 时变、星间、双站互视、对星扫描又各有一套采样器——**全平台 6 套独立扫描实现、口径不一**（运管任务书 §2.2 第 6 条只点到两套）。
- **量级**（B 路实测，真值 = 同函数 1 s 粗扫）：Walker 550 km / 53°（6 × 22 颗，北京，72 h）门限 25° 漏检 1.75%，**最长中断 11.81 min vs 真值 3.44 min（3.4 倍）**；门限 40° 漏检 6.04%、时间覆盖 −0.79 pp、最长中断 85.1 vs 76.7 min。24 颗 850 km / 45°（物联网量级）海口 20°、7 天：最长间隔 30.4 vs 14.9 min（2.0 倍）。覆盖 FOM 单格（北京 1° 格，132 颗，25°，24 h，60 s 采样）：访问次数 119 vs 168（−29%）、最大重访 4.00 vs 3.18 min（+26%）、平均间隔 1.71 vs 1.20 min（+43%）；时间覆盖率本身只差 0.1 pp。记忆里「1 s 真值交叉验证最大偏差 0.022 pp」只验了时间覆盖率、算例稀疏门限低，稠密星座高门限下不成立。而物联网星座评估、关口站接触计划、星座设计最常看的正是重访、最长中断、接触次数。
- **最佳实现**：唯一访问引擎 `packages/core/utils/access/`（纯函数，主进程与 Worker 共用），`visibility.accessWindows`、`solveAccessWindows`、`coupledTypicalMoment`、ciNgso 服务星扫描、`coverageGrid` 全部改调它。单目标事件用「仰角极值夹逼 + Lipschitz 自适应步长」：按 Δ = min(P/16, 5 min) 找离散局部极大 → 黄金分割 / Brent 精炼峰值到 0.1 s → 峰值 ≥ 门限才成窗、在单调段上求 AOS / LOS（1 ms）；多约束时 g(t) 取各约束归一化余量的最小值；步长取 max(Δmin, |g| / |ġ|max)（即 satcovScan 的「球面追踪」，可证不漏）；GEO 按采样极差判常驻。**原型已验证**（B 路 extremum_proto.mjs）：同一 132 颗 72 h 算例，25° / 40° 下过境 1202/1202、712/712 全中，时间覆盖与最长中断和 1 s 真值一致到 0.001 pp / 0.01 min，SGP4 调用约为生产路径的一半，耗时同量级（约 150 ms）。覆盖 FOM 区间精确化：保留散射核，只对「状态翻转的格」与「被星下点轨迹扫过但两端都未覆盖的格」用 Hermite 插值星下点求解精确进出时刻，FOM 由逐格区间表扫线算出。结果区加读数「最小可检出过境时长」。
- **验证**：1 s 与 0.1 s 暴力扫描（随机星座 × 随机格 × 门限 5–60°，断言 0 漏检、边界差 < 0.1 s）；单星非旋转地球解析过境时长；本机 STK 12 同 TLE 出 Access / Coverage 报告逐窗对拍。迁移 ciNgso 要守「CDF 等权粗采样 / in-line 细化」两套采样率；`coupledTypicalMoment` 的 t* 必须逐位回归。

### B-02 覆盖网格与分析目标几何：跨日界线算成补集，「质心」是顶点均值 〔跨日界线 + 质心 P0 · S；其余 P1 · M〕
- **现状（已核并复跑脚本）**：`makeCoverageGrid` 的 Polygon 与边界直接用原始经度（coverageGrid.js:37-45 射线法未做经度展开，注释写「协调区一般不跨越经度断裂线」）。170°E → 170°W、0–20°N 的 Polygon 按 2° 网格应为 100 格，**实际得 1700 格**（算成另一侧 340° 宽的补集）；同范围用「自定义边界」得 0 格。可见性「Polygon（质心）」用顶点算术平均 `ringCentroid`（visibility.js:15-28）：跨日界线那块的「质心」落在 (0°, 10°N)（地球另一面）；南海一块顶点疏密不匀的区域与面积质心差约 310 km。建链模块已有正确实现 `pgRing / pgContains / pgCentroid`（mapLinkPoints.mjs:71-215，同两例给 (180°, 9.95°N) 与 (115.46°E, 13.86°N)）——又一个孤岛。本机波束里有 77 个跨日界线（《相对 v1.5.2 改动审查》#15），太平洋海事航空区域是常规输入。
- **最佳实现**：网格与目标统一改用 `pgRing` / `pgContains`，边界 lonMin > lonMax 视为跨日界线，`ringCentroid` 换 `pgCentroid`（Polygon 边按经纬线性画，判定同口径、不换大圆）；面目标访问四档语义（质心 / 任一点 / 全部点 / 面积覆盖百分比）；网格加纬度带等面积网格作缺省（Δλ = Δ / cos φ），H3 可选（Apache-2.0，许可未核实）；点集网格（城市库 / 地球站 / CSV / 航迹采样点）；格点高度（航路 FL）与站点海拔（取 DEM）进入观测者高度；多目标访问（任一 / 全部 / k-of-n）。验证：跨日界线 Polygon 格数 = 同尺寸非跨线格数；STK 12 Area Target 对拍。

### B-05 地形 / 建筑遮挡：没有地平线掩模，Earth2014 5′ 也撑不起 〔P1 · L〕
- **现状**：地形只用于取站点海拔；所有可见性在光滑椭球上做；grep horizonMask / terrainMask 零命中。
- **量级**（用平台自带 Earth2014、4/3 等效地球算 360° 地平线）：拉萨站高被平滑成 3881 m、最大地平线仰角只有 4.56°；香港 0.80°、昆明 0.97°、密云 2.41°、北京 0.77°——5′（约 9 km）网格把 10 km 内近场山体抹平（例：太平山距中环约 2 km，几何上约 15°，未用 DEM 核实）。结论：Earth2014 只能当远场数据；对 5–10° 门限的关口站选址、西部山区站、高纬船站看 GEO，平台会高估可见时段。

### B-06 覆盖 FOM 目录、统计口径与数值导出 〔P1 · L〕
- **现状**：7 个 FOM；KPI 只有面积加权时间覆盖、最差格、覆盖面积；热力图静态；**没有任何数值导出**（只能整图出 PNG / PDF）；无人口 / 需求加权、无 DOP。

### B-07 移动平台：只有位置，没有终端姿态、视场、运动多普勒 〔P1 · XL〕
- **现状**：航迹运动学扎实（大圆 + Vincenty + 时刻钉点 + 剖面），但**滚转恒 0、转弯在航点瞬时完成**（entityPose.mjs:218-224 注释原话），姿态只被 3D 渲染层用；可见性引擎支持移动目标，但面板下拉里没有航迹；多普勒只按静止站算（ngsoGeometry.js:237-263）。
- **量级**：飞机 250 m/s 自身多普勒 Ku 14.5 GHz ±12.1 kHz、Ka 30 GHz ±25.0 kHz——GEO 航空链路里这是唯一的多普勒来源，平台给 0。转弯滚转 φ 时背向卫星一侧的机体系仰角 ≈ 当地仰角 − φ；高纬航路 GEO 仰角 20–30°，15–30° 滚转就能把它压到地平附近，机背平板很可能超出视场而断链——平台看不到也量不出。
- **最佳实现**：航点处插入协调转弯圆弧 R = V² / (g·tanφ)；船舶给横摇 / 纵摇幅值与周期或导入姿态时间序列（含 ADS-B / AIS），没有新字段的旧航迹逐位不变；`terminalGeom.mjs`：输入载体姿态与星位，输出挂点系方位 / 俯仰、扫描角、机体系仰角、含滚转的极化偏转角、计入载具速度的距离变化率；视场与机体系仰角作为约束进 B-03；输出「航迹剖面」逐拍表（时刻、姿态、服务星 / 波束、各类角、多普勒、约束余量、切换事件，可导 Excel），放在性能表或过境模式里，不进四个链路预算窗。**边界**：只出几何量；扫描损失、多普勒实现损失不进链路预算（2026-07-23 拍板「不是问题」）；这是分析能力，与「不做动中通」的硬件路线无关。

### B-08 可见性 ↔ 链路预算：结果不带时间，链路可达时段没有 〔P1 · M（可达时段另 2–3 天）〕

### C-01 气体吸收：比衰减仍用 P.676 已删除的旧闭式，输入口径过粗 〔P0 · L〕
- **现状（已核）**：γ_o、γ_w 用 P.676-9/10 Annex 2 式(22)(23)，等效高度用 P.676-13，注释自认「混搭」；NGSO 引擎同样；输入 Ts 按纬度三档、ρ 晴天取 RHO_90 / 雨天取 RHO_10、无 VSCH 高度订正、未用 P.2145 与 P.1510；p676Data.js:708 的 P676_PART2 没有任何调用方。
- **差距**：P.676-13 Annex 2 规定 γ 用 Annex 1 逐线法（44 条氧气线、35 条水汽线）；P.618-14 §2.5 规定无本地分位数据时用平均气体衰减，并按式(68) 取 A_G(p) = A_G(5%)；P.2145-0 给出 Ps、Ts、ρ、V 的年 / 月统计图。

### C-02 天空噪温分项相加，违反 P.618 §3 式(69) 〔P0 · S–M〕
- **现状（已核）**：「自动」天线噪温只用气体衰减 A_G（:665）；云噪 275(1−10^(−A_C/10)) 单独计入系统噪温（:674 / 678）；雨噪单独计入 G/T 劣化（:669, 688-689）；NGSO 引擎同样；手填噪温时雨噪、云噪同样直接叠加。
- **差距**：式(69) T_sky = T_mr(1−10^(−A/10)) + 2.7·10^(−A/10)，A 为除闪烁外的总衰减——串联介质必须先合成衰减再算噪温；式(70) T_mr = 37.34 + 0.81·Ts。
- **量级**：广州 20 GHz 99.9%（A_G 0.84、A_C 0.32、A_R 14.73 dB）分项相加得 335.9 K，按式(69) 合成应为 268.0 K；1.2 m 站系统噪温 431 K vs 368 K，**雨致 G/T 劣化多算 0.69 dB**（广州 99.5% 多 0.62、北京 99.9% 多 0.60、北京 99.5% 多 0.48）；Ka / Q 下行降雨工况的 DND、功放建议、占用率因此偏保守。
- **最佳实现**：单一函数 `itu/p618.skyNoise({A_G, A_C, A_R, Ts})`，系统噪温由它统一构造，雨致劣化 = 10lg(T_sys(p) / T_sys(晴))；手填噪温拆成「天空部分 + 地面拾取」只对天空部分施加衰减（拆分口径写 title）；T_mr 用 P.1510 地表温度按式(70)；**100% 可用度下 A_C = A_R = 0，现有回归基线逐位不变**；雨衰页 rainAttenuation.js:265-273 同步改用。验证：恒等式断言（T_sky ≤ T_mr；A → 0 退化晴空；A → ∞ 趋于 T_mr）+ 单调性扫描。

## 5 干扰、频谱与 ITU 规则（D 路）

### D-01 AP8 ΔT/T 只算了上行一半，却按「RR 附录 8，门限 6%」出数 〔P0 · L〕

### E-01 自产多波束方向图无旁瓣且截窗，用于 C/I 系统性高估 〔P0 · L〕
- **现状（已核）**：多馈源组 `buildGaussGrd` 纯高斯、窗口半宽 1.8θ3、地板 −50 dB（synth.js:393-400）；STK 高斯组窗口 2θ3、主瓣外无旁瓣；赋形的成分波束是高斯；PAM 均匀激励、窗口 4θ3；`solveReflector` 已解出口径边缘照射 p，却只用来换算 θ3 与峰值增益、没有用来生成方向图；窗外采样返回 null，C/CCI 遇到 null 直接跳过（ciCci.js:91-92）。
- **量级**（E 路实测）：理想蜂窝（间距 0.866θ3、4 色）波束中心 C/I：高斯 28.3 dB，同 θ3 的 −10 dB 锥度口径只有 15.0 dB；7 色三重点高斯 35.8 dB、口径 15.3–19.8 dB。**真实 HTS 数据**（用户库 EIRP_OK1，62 个窄波束 θ3 约 0.60°，几何 4 色着色）：真实方向图 C/CCI 中位 27.4 dB、5% 分位 21.0 dB；换成同峰值同 θ3 的平台高斯复制品后中位 48.3 dB、5% 分位 27.3 dB，且 44% 的服务区报「无同色」（7 色时 87% 留空）。**结论：用平台自己设计的 HTS 波束做干扰评估，结论不可用。**
- **最佳实现**：新增「口径照射模型」作为新的解析天线种类（旧高斯模型逐位保留守回归）：F(u) = (2pΛ₁ + qΛ₂)/(2p + q)、u = πD·sinθ/λ，按各波束自身视轴的真实离轴角计算，p 直接取 `solveReflector` 结果（θ3 与效率同源）；补偏轴馈源波束偏移因子（BDF 已有）与扫描像差损失、表面误差决定的零点填充与远旁瓣地板（Ruze 公式，或以 S.672-4 rec.1 / S.1528-1 包络作下界）、交叉极化（线极化用偏置反射面去极化闭式 Chu–Turrin，圆极化用波束斜视 Adatia–Rudge）；把 gaussStk 的解析记录推广为带 `model` 字段的通用记录，在 `coverage.samplePowAt` 的 `beam.an` 分支与 `grdSampler.sampleBeamAt` 闭式求值、不截窗。赋形改用新成分波束会改变既有出图，必须走新模型档。
- **验证**：闭式与数值口径辐射积分对比（−40 dB 以内误差 ≤ 0.01 dB）；本机 SATSOFT 3.2.0 多馈源反射面 AR / PO 模型导出 GRD 比主瓣、首旁瓣、C/CCI 统计；EIRP_OK1 统计作回归参照（−14 / −18 dB 锥度复制品已能把中位做到真实值 −1.8 / −0.5 dB）。

### E-03 极化口径：AR 的 icomp 基用反、Xpol 列固定 P1−P2、合成与解析件无交叉极化 〔P0 · M〕
- **现状（已核）**：`axialRatioDb`（coverage.js:662-679）把 icomp = 3 当圆极化基（R/L），icomp = 1 / 2 走线极化 Stokes 支路——与平台自己的《GRD 格式解析说明》（2 = RHC / LHC，3 = Ludwig-3 co / cx）和 TICRA 定义正好相反；Xpol 列固定为 P1 − P2（usePerfTable.js:577），选项框把 P1 写成「共极化」；主进程已有按峰值判共极化的 `coPolIndexOf`，渲染端没用；该函数无单测。
- **量级**（E 路实测）：EIRP_OK1（icomp = 2，Ka 圆极化）AR 显示 60 dB、真值 0.098 dB；300_X02G（icomp = 3，Ku 线极化）AR 显示 0.21 dB、真值 59.75 dB；合成件（icomp = 3、分量 2 恒 0）AR 显示 0 dB，应为 ∞（SATSOFT 报 400 dB）；Xpol 在两份真实文件上报 −44.98 / −38.29 dB（共极化在分量 2，94 个波束全是）。
- **最佳实现**：统一极化内核覆盖 icomp 1 / 2 / 3 / 4 的基互换；共极化按峰值判定（复用 coPolIndexOf）、允许用户钉死；线极化做 τ 自动旋转（E1 = P1 cosτ + P2 sinτ，SATSOFT §3.4.5）；XPD 一律报正值；AR 先换到圆极化基再算；合成件写入 E-01 交叉极化模型；纯标量件报 400。验证：已知极化椭圆闭式测试向量（四种 icomp）；本机 SATSOFT 对同一 GRD 同一批城市输出 AR / Xpol 列逐行对比。修正后既有表中 AR 数值会变（纠错）。

## 8 业务链覆盖与市场定位（H 路）

### 8.5 「完美工具」的产品形态

**做**：
- 一个引擎 + 三层数据：公开数据包（星历、ITU 数据）/ 运营商私有星队数据包（GRD、频率计划，按密级管理，只装进内部版）/ 用户工程。
- 四种交付形态：Windows 标准版；离线 KA 版（无云功能，.lic 或浮动许可）；信创 Linux 版；CLI / SDK。
- 六个业务工作台：售前方案（已有）、频率兼容分析与申报、GSO 运行预报（日凌 / 星蚀 / 倾斜）、HTS 容量、站址评估、监测对照。
- 服务：验证档案、手册、培训、工单。

**明确不做**（交给专业软件或官方工具）：EPFD 自校验（ITU EPFD Prepare / Static，平台停在上游只出掩模）；AP4 录入与校验、GIMS 校验、GIBC 官方判定、AP30 / 30A / 30B 规划（只做数据准备与对拍）；7×24 载波监测、CID 解码、干扰源地理定位（Monics / satID；定位法定属国家无线电监测中心）；测控指令、遥测、FDIR、地面站 M&C；精密定轨的运行服务、站保机动的执行（平台做规划级预报与 what-if，见 A-02，只读飞控输出的星历与机动计划）；实时动态资源控制与网络编排（Kythera / Aalyria / iDirect Intuition，平台只做规划级）；计费 / 合同 / CRM 台账（BOSS 系统；09-01 回退的「频率管理」不重建）；PO / 全波级天线电磁设计（GRASP / POS，只做导入）；星间链路路由（08 月已回退）。

**理由**：竞品要么强在轨道（STK、ATK），要么强在监管（Visualyse、BR），要么强在天线（SATSOFT），要么强在运行系统（Kratos、GMV、Kythera）；没有一家把「运营商视角的规划 → 交付」串起来，这就是护城河。实时系统与官方判定做了也不被承认，应交出去。

### G-01 更新链路无签名、安装包未签名、全员静默安装 〔P0 · 清单签名 M / Authenticode L / CAM S〕
- **现状（已核）**：updater.js:172 / 174 `autoDownload = true`、`autoInstallOnAppQuit = true`，退出时 `--updated /S` 静默装，另有启动补装；`app-update.yml` 只有 provider / url / cacheDir，无 `publisherName`（electron-updater 因此跳过签名校验）；安装包与主 exe `Get-AuthenticodeSignature` 均 NotSigned（G 路）；平台侧没有管理端 v1.2.0 那套 Ed25519 清单签名；发版密钥是「在线分享」子账号，07-03 起放开 updates/* 写，常驻两台日常机的用户环境变量。
- **影响**：谁拿到 updates/ 的写权限（开发机环境变量泄露、COS 主账号失守、随包钥匙被误授权），谁就能让全部装机（同事与 KA 客户）在下次关闭软件时**无提示执行任意 exe**。未签名安装包触发 SmartScreen「未知发布者」，启用 AppLocker / WDAC 的国企终端直接不能运行。
- **最佳实现**：① 移植管理端 `updateSig.js` 口径：独立发版签名钥（Ed25519，离线保存，`UPDATE_PUBKEYS` 数组可轮换）签 `satsim-update|v1|version|url|sha512|size` 写进 latest.yml；updater 改 `autoDownload = false`，update-available 时验签、过了再 `downloadUpdate()`，下载后核字节数与 sha512 才挂退出安装，拒绝降级。② Authenticode：签主 exe、NSIS 安装 / 卸载器、elevate.exe，加 RFC 3161 时间戳（CA/B 论坛 2023-06 起 OV / EV 私钥须放 HSM 或令牌）；`publisherName` 写进 app-update.yml 让 electron-updater 再验一次。③ CAM 拆分：发版专用子账号只给 updates/* 写、开 MFA、限来源 IP；「在线分享」子账号收回 updates/*；updates/ 开对象版本控制 + 操作审计告警。④ latest.yml 用 `stagingPercentage` 灰度并备回滚。⑤ dist 上传前签名自检，失败中断。
- **验证**：.updharness 加管理端四情形（签名对→装；无签名→不下载；包被换→sha512 不符；未发版→idle）+ 降级拒收；`Get-AuthenticodeSignature` = Valid。首个带验签版本只能经旧逻辑装上，需过渡一版；公钥数组预置备用钥。

### G-08 发版工程：没有 CI，dist 不跑测试，不是干净构建，没有溯源 〔P1 · L〕
- **现状**：无 `.github`、hooks、lint、类型检查；dist（package.json:23）不含 `npm test`、`--check`、i18n 扫描；`check-untracked.mjs:19` 只查 `--others`——已修改未提交的文件（会话开始时 145 个 M）照样进包；在多会话共用工作树上直接构建、用本机被 patch-nsis 改过的 node_modules，没有 `npm ci`；Node 未钉版本（测试跑 Node 22.14、生产主进程 Node 20.18）；发版提交叫「工作区全量入库」（v1.5.0 一次 415 文件、+50,542 行）；v1.4.9 无 tag；发版清单只存在记忆里。

### G-09 数据持久化：工程数据在 localStorage，无 schema 版本、备份与迁移，userData 在 Roaming 〔P1 · XL，与 F-01 / F-02 合并实施〕
- **现状**：主进程侧好（`jsonStore.js` 先写 tmp、留 .bak、再 rename；`storage.js` 读坏拒写；配置分 9 份各 30 档版本）；但核心工程数据在渲染端 localStorage（`globe3d/polygons`、`globe3d/markers`、`globe3d/beamSynth`、`constellation3d/customConsts`、`satSets`、`satGroups`、`globe3d/grdSats`、`grdLive`、55 键 `globe3d/settings`……约 100 个键、引用 459 处；grep `QuotaExceeded` 为 0）；只有模型子系统有 `schema: 1`，其余靠约 15 个 `migrate*` / `legacy*` 按形状猜；`storage.js:2` 与 `package.json:4` 写着 SQLite 但从没实现；无工作区备份与换机路径；`%APPDATA%\satellite-sim-platform` 共 3.9 GB（导入 GRD 3.0 GB、Cache 329 MB、Code Cache 319 MB、gfs-cache 201 MB）。

- **最佳实现**：主进程持有工作区库（`node:sqlite` 或 better-sqlite3，WAL，各实体建表，`schema_version` + 有序迁移脚本 `electron/services/db/migrations/`，用 v1.5.0–1.5.3 夹具库做迁移测试）——这就是 F-01 sceneStore 的落盘层，各窗口改走 IPC + 变更事件，顺带根治跨窗口互相覆盖；缓存类移 `%LOCALAPPDATA%`，数据目录可由企业策略指定；SQLite 在线备份做每日轮转（7 日 + 4 周）；每个结果 / 报告记 appVersion、引擎提交号、数据集 id 与哈希、输入哈希；localStorage → 库一次性迁移保留旧值直到确认，逐字节往返测试。验证：千次随机写 + 强杀，integrity_check 通过、损失不超过最后一个事务。
