# 任务书：2D 平面图手势期重建治理（拖动 / 缩放的延迟与小卡顿）

日期 2026-09-06。执行者：Opus。发起人：朴东旭。本任务书自带全部上下文，不依赖对话历史。
前一份任务书 `docs/2D视图整体流畅化任务书_2026-09-06.md`（Phase 0–2 已执行并提交：c21ef87、6be5bf9）把静态层从「每帧重建」压到「每手势一次」。本任务书治的是它之后仍然存在的「拖动 / 缩放有点延迟、有小卡顿」——根因是**那一次重建仍然很贵，而且现在有四条路让它在一次手势里发生好几次**。用户要求：**最佳效果**，不是最小改动。

## 0. 一句话目标

`src/viz/flatmap/flatCoverage.js` 的 2D 平面图，在四个代表配置（出厂「高」= 50m + 瓦片影像 + 等距圆柱；「超高」= 10m + 瓦片；10m 影像关；方位等距 + 16K + 10m）下：

- **手势进行中**（拖动、滚轮连续或慢速逐格、进度条缩放、缩小回全图）每一帧 ≤ 8 ms 主线程、帧间隔 ≤ 20 ms（验证台口径，见 §6），**期间 0 次整份重建**（只有实测代价 < 8 ms 的「真廉价」视角例外，那时同步重建也在预算内）；
- **手势静止后恰好一次重建**，并且这一次在宽视角下要从 100 多毫秒降到 ≤ 10 ms（§4.6 自动综合），窄视角本来就便宜；
- 缩小回全图时**不出现深色空环**，画面永远有东西；
- 静止画面、导出 PNG/PDF、3D、GRD 填充 GPU 路、STK 热力图、对星壳层覆盖：不变式与前一份任务书 §4.5 相同。

## 1. 现象与根因（2026-09-06 实测，执行前不必重测）

尺子：`.imgharness`（1280×720 CSS @ DPR 1.5 = 1920×1080 设备像素，`img-harness-alt` 5934 端口，5933 常被别的会话占着）。所有数字都是当前工作树（HEAD 963d185，`flatCoverage.js` 无未提交改动）量出来的。

### 1.1 一次重建到底多贵：主线程读到的和真实代价差一个数量级

`renderStaticLayers()`（2000 行）末尾记的 `lastRebuildMs` 是**主线程同步耗时**。Chromium 现在把 canvas 光栅放在别的线程，主线程只记录绘制指令，真实代价落在**紧随其后那一帧**的等待里（下一帧要等上一帧的光栅排完才能开始）。探针：重建一帧之后再连着请求两帧，看哪一帧被顶住。

| 场景（全图视角） | `lastRebuildMs`（主线程） | 后一帧等待（真实代价） |
|---|---|---|
| 10m · 影像关 · 等距圆柱 | 5.5～6 ms | **118～132 ms** |
| 10m · 瓦片 · 等距圆柱 | 3～3.5 ms | **104～106 ms** |
| 10m · 16K · 方位等距 | 3～4 ms | **90～158 ms** |
| 50m · 瓦片 · 等距圆柱（出厂「高」） | 1.6 ms | **29～30 ms** |

同一场景的主线程读数在 3～12 ms 之间抖（Chromium 的 canvas 加速模式会自己在同步 / 异步光栅之间切，前一份任务书 §7.2 记过）。**这个读数正好跨在 `REBUILD_FAST_MS = 8` 的门槛上。**

### 1.2 四条让「一次手势」里发生多次重建的路

`draw()`（2262 行）的判定：

```
if (!pl || (pl.scaled && lastRebuildMs < REBUILD_FAST_MS)) { renderStaticLayers() ... mode = 'rebuild' }
```

1. **缩放期「便宜就同步重建」判据失效（头号）**。它的本意是放大视角 / 50m 档重建只要 1～2 ms、直接重建比缩位图更清楚。现在所有档都读到 1.5～6 ms，全被判成便宜 → **缩放每一帧都整份重建**，代价按 §1.1 的右列付。实测：出厂 50m + 瓦片，10 帧 10 次 `rebuild:fast`，帧间隔 2～4 ms 与 47～73 ms 交替；10m + 瓦片一次跑 10/10 缩位图（顺），另一次前 5 帧 `rebuild:fast` 出现 312 / 186 ms，后 5 帧因为某次读数 ≥ 8 又切回缩位图 —— 观感忽好忽坏就是它。
2. **慢速滚轮撞上静止补建**。`IDLE_MS = 110`（475 行），手滚一格的间隔常在 100～300 ms，超过 110 就在两格之间补一次重建（或这一格本身走 `rebuild:fast`），下一格的帧要等它的光栅。10m 无影像 8 格（间隔 150 ms）里 4 格 106～204 ms；方位等距 + 16K 出现 171 / 296 / 578 ms（578 那格还撞上分辨率跨 2 的幂档的网格重规划 68 ms + 8192 纹理）。
3. **拖动中间停一下**。DPR 1.25 / 1.5 下位移落不到整设备像素，`snapPlace()` 的 `exact` 为假 → `scheduleRebuild()` → 停 110 ms 就补一次 → 再拖的第一帧等它的光栅。DPR 1.25 实测每次停顿后第一帧 38～42 ms（1600×900），1.5 + 10m 约 100 ms。DPR 1 / 2 没有这一项。
4. **放大视角往外缩**。快照余量每边 `OVER = 0.18`（464 行），滚轮一格 exp(0.15) = 16%，两格就盖不住 → `rebuild:uncovered`（同步重建）。方位等距从 t=0.45 缩出 10 步：3 次重建，单帧 47～277 ms。

次要：瓦片到货 `onTileReady`（904 行）60 ms 去抖后整份重建，放大跨级时几批连着来；`ctx.filter = brightness()`（883 行）在亮度 ≠ 1 时逐片走滤镜层。夹层每帧重画（GRD 等值线 Path2D 描边、聚焦星轨迹 / 覆盖圈、晨昏线）与 `pointermove → cursor → App.vue` 状态栏重渲染在验证台里量不到，量级小。

**平移本身没问题**：快照 blit 一帧 0.1～0.4 ms，8/8 blit。

### 1.3 为什么 Phase 1 没治好

它把重建从「每帧」压到「每手势一次」，但上面四条路让一次手势里仍发生多次；而 10m 全图一次重建就是 100 多毫秒的 GPU 光栅——前一份任务书 §1.3 说的五类边界线 48 万点描边成本，Phase 3 没做，它还在。所以本任务书分两层：**调度层**（手势期绝不同步重建，§4.1–4.5）与**内容层**（让那一次重建本身便宜，§4.6–4.8）。两层都做才是「最佳效果」：只做调度层，缩放期是缩位图（糊）、静止后有一次 100 ms 的顶住；只做内容层，四条路仍在。

## 4. 设计

### 4.1 重建代价按「光栅」口径量，不按主线程口径（调度层，根因一）

- 每次 `renderStaticLayers()` 之后，在 `draw()` 里排一个**探针帧**：`const tEnd = performance.now(); requestAnimationFrame(() => { rasterGapMs = performance.now() - tEnd; ... })`。探针只在重建那一帧排一次，不是常驻 rAF 循环。它排在 `draw()` 内部，所以一定是下一帧的第一个回调，量到的就是「下一帧被顶住了多久」。
- 真机 rAF 对齐 vsync，便宜的重建 gap ≈ 一个刷新周期（60 Hz 16.7、144 Hz 6.9）；验证台没有 vsync，gap ≈ 0～3。故 `nominal` = 迄今探针 gap 的滚动最小值（初值 16.7，钳在 [4, 20]），`rasterExtra = max(0, gap − nominal)`，**`costEst = max(lastRebuildMs, rasterExtra)`**。Chromium 切回同步光栅模式时 `lastRebuildMs` 自己就是 100 ms，两种模式都能读对。
- 代价按**视角类**记：`cls = detail + '|' + (imgOn ? 'img' : '') + '|' + PJ.kind + '|' + Math.round(Math.log2(k()·dpr) × 2)`（半倍频程一档）。`costByCls[cls] = costEst`，换到没量过的类一律**当作贵**（走缩位图，静止后量到再说）。迟滞：贵→便宜要连续两次 < 8 ms，便宜→贵一次 ≥ 8 ms 即翻。
- `draw()` 判定改成：

```
cheap = costByCls[cls] 已知且 < REBUILD_FAST_MS
zoomIn = kk > snapK
if (!staticValid)                       → 重建（内容变了，无条件）
else if (pl && !pl.scaled)              → blit（平移）
else if (pl && pl.scaled && cheap && zoomIn) → 同步重建（真廉价的放大：清晰优先）
else if (pl)                            → 缩位图 + scheduleRebuild
else /* 盖不住 */                       → §4.4：有回退快照就合成；没有且 cheap → 同步重建；没有且贵 → 海色垫底 + 缩位图 + scheduleRebuild
```

  **缩小一律不走同步重建**（缩小是降采样，缩位图不糊；放大才有清晰度收益）。

### 4.2 平移不再产生静止补建（根因三）

- 交互平移把 `tx/ty` **量化到整设备像素**：`onMove` dragging 分支与 `panByPixels` 末尾 `tx = Math.round(tx * dpr) / dpr; ty = ...`（用模块级 `dpr`，不是 `window.devicePixelRatio`）。位移永远整像素 → `exact` 恒真 → 拖动全程 0 次补建。每次按最近整数量化，误差不累积。
- 同时在 `renderStaticLayers()` 开头也量化一次（记 `snapTx` 之前）：不然缩放静止后 `snapTx` 是分数、第一次拖动的残差又是 0.5 px。静止重建时挪 ≤ 0.5 设备像素肉眼不可见；缩放锚点的精度只在缩放进行中有意义。
- `fit()` / `setView()` / `onWheel` / `setZoomT` **不量化**（它们要精确的居中 / 锚点数学）。
- 逐像素闸的口径随之改：blit 出来的静止画面 = 在**同一个量化后的视图**上现画一遍。`pxdiff` 比对时先从当前版 `getView()` 读出视图再 `setView` 喂给基线版（不要两边各自 `panByPixels(12)`——基线不量化，两边视图会差 ≤ 0.5 px 而比出满屏假差异）。`exact` 的容差 1e-9 保留。

### 4.3 静止补建与手势错开（根因二）

- `IDLE_MS` 改成自适应：`idle = clamp(2.5 × costByCls[cls], 110, 350)`；便宜的视角 110 ms 后就清晰，贵的视角多等一点、避开滚轮格间隔。
- 手势热度：`gestureHot()` = `dragging` 为真，或距上一次 `onWheel/setZoomT` 不足 `idle`。补建计时器只在不热时到期；指针按着（拖动中停顿）**不补建**，`onUp` 之后按 `idle` 再补。
- 补建到期时若 `costByCls` 判贵且用户正在……（不用再判，到期就是静止）——到期只做一件事：`invalidateStatic()` 的**视图版**（§4.5）+ `requestDraw()`。

### 4.4 缩小回全图不再盖不住（根因四）：保留上一张快照当回退

- **保留而不是丢弃**：重建时若旧快照的内容代（`gen`，§4.5）与新的相同，且旧快照在世界坐标里的覆盖不是新快照的子集（典型：从全图放大进来，旧的那张是全图），就把旧的两张画布连同 `k/tx/ty/mx/my/gen` 挪进 `fallbacks[]`（上限 2 对，按覆盖面积保留最大的；`resizeNow` 与内容作废时清空）。新快照另起画布（双缓冲），别再复用同一张。
- `snapPlace()` 返回 null 时，从 `fallbacks` 里找覆盖「世界矩形 ∩ 视口」的那一张（同一套判据，按它的 `k` 缩）：先画它，再把当前快照缩着画在上面。**above 层的回退要用 evenodd 裁剪只画到当前快照矩形之外的那一圈**（`rect(视口) + rect(当前快照缩后矩形)` + `clip('evenodd')`），否则地名 / 边界线会在重叠区叠成两层、略有错位。below 层不裁也行（上层盖住）。
- 一张都盖不住（内容刚变过、还没来得及重建）：先用 `oceanColor` 把世界范围填一遍（等距圆柱是 `worldRect`，投影档是 `sphPath` 的路径）再缩位图、`scheduleRebuild`——露出的那一圈是海色而不是深色背景，静止后 ≤ 350 ms 归位。这条只在 §4.1 「没有回退且贵」的分支走。
- 最常见的用法（从全图放大看某区域再滚回来）只需要 1 张回退 = 放大之前那张全图快照，**零额外重建**。内存：每对 ≈ 2 × 1920×1080×1.36² × 4 B ≈ 32 MB，两对 64 MB，桌面端可接受；`resizeNow` 时释放。

### 4.5 「内容作废」与「视图补建」分家

`invalidateStatic()` 现有 29 处调用，**全部是内容变了**（地名档 / 边界样式 / 标记 / 卫星层 / 换平面 / 瓦片到货 / 后端变 / 视角广播 / `resizeNow` / `reset` / `onDbl`……），它们要：`gen++`、清空 `fallbacks`、`staticValid = false`。**只有 `scheduleRebuild` 到期那一条是视图补建**：内容没变，`gen` 不动、`fallbacks` 保留、只 `staticValid = false`。写成两个函数（`invalidateStatic()` 与 `rebuildAtRest()`），别用参数区分——29 处一处都不用改。

瓦片到货（`onTileReady`）：`gestureHot()` 时只记 `tilesDirty = true` 不作废；静止补建时顺带把它清掉（补建本来就重画瓦片）；不热时照旧 60 ms 去抖（可拉到 120 ms，一批次一次）。`rotLive`（拖动调整中心）那条路不动。

### 4.6 宽视角自动用 50m（内容层，让那一次重建本身便宜）——★ 唯一的口径改变，见 §9 拍板

前一份任务书 §4.4 提过、当时留给用户拍板；现在「最佳效果」要求下它是主菜：**10m 全图重建 100 多毫秒的账，只有不画 10m 才消得掉**（Phase 3 GPU 线是另一条路，风险与工作量都大得多，本任务书不做，只给 go/no-go 数据）。

- 判据：`pxPerDeg = k() × dpr`（平面单位就是度，投影档取中心处的尺度即可）。`pxPerDeg < T` 用 50m，否则用用户选的档（10m）。**110m 永远不许自动选到**（没有争议面图层）。只在**静止重建**时换档，手势中不换（缩位图期间换档等于换内容）；迟滞 ±10% 免得在门槛上来回跳。
- **T 要校准，不许拍脑袋**：在验证台把 50m 与 10m 在同一视图各画一张（影像关、地名关、只有海陆 + 五类线），对 pxPerDeg = 5 / 8 / 12 / 16 / 20 / 30 逐像素比，记「差异像素占世界矩形的比例」与「最大连通差异块的像素数」（小岛消失就是一块）。T 取「差异比例 < 0.3% 且最大块 < 40 px」的最小 pxPerDeg；**四张截图（T 之下两档、T 之上两档）进报告**。预期 T 在 12～20 px/° 附近（全图是 5.3，中国全境约 20）。
- 两档的烘制结果**同时缓存**（`baseGeo[detail]`、`borderPaths[detail]`；行政区界 `admPaths` 与档无关），换档时 O(1)，不重新 `buildBaseGeo`。`buildBaseGeo` 现在写模块级状态，要改成按档存取；`mapDetail0` 语义不变 = 用户选的上限，自动只会 ≤ 它。`labelSet` 若随档不同（查 `povResolver.labelSet`），地名按用户选的档取，不跟自动档走（地名密度不该随缩放跳）。
- **导出不受影响**：`exportFlat.js` 的 `withFinestBasemap` 强制 10m，`exportRender` 走 `mapDetail0`，自动档只在屏上生效。3D 不动。
- 中间带（T 之上、10m 可见顶点仍多，例如看整个欧亚）静止重建可能仍 30～60 ms：**量出「10m 重建代价 vs pxPerDeg」曲线**进报告。若某带 > 16 ms，可选做「按带缓存的抽稀」：`mapThin = 0.5 / pxPerDeg`（度）按半倍频程分带各烘一份 Path2D（≤ 8 份），静止重建按带取。这一步按实测决定做不做，先把曲线拿出来。
- 开关：画质档「自定义」里加一行拨杆（`.layersw` 那种，**无说明文字**，CLAUDE.md），字段 `mapAuto`，`PRESETS.ultra / native` 为 `true`、`high / mid / low` 本来就是 50m 无所谓；`displayQuality.js` 与宿主 4337 那一行只是多传一个布尔——宿主那一行在别的会话未提交的文件里，**只加这一处最小改动**，不碰别的。

### 4.7 让带影像的重建便宜（内容层，50m + 瓦片那 30 ms）

50m 全图重建主线程 1.6 ms、光栅 29～30 ms。15 片 512² 的 `drawImage` 加两次整幅拷贝在 GPU 上不该要 30 ms，先归因再改，三条候选按序试、每条独立计量、无效就撤：

1. **余量为 0 时也直接渲到离屏画布**，省掉 `belowCtx.drawImage(canvas)` / `aboveCtx.drawImage(canvas)` 两次整幅拷贝（2000 行那条「原样走老路」的分支）。带余量那条路本来就是直接渲到离屏、且过了逐像素闸，故预期逐像素相同；**用 `pxdiff` 证明**，不同就撤。
2. **瓦片改存 `ImageBitmap`**（`imageryTiles.js` 的 `img.onload` 后 `createImageBitmap(img)`，解码离开主线程；缓存里存 bitmap，`getTile` 返回值形状不变）。前一份任务书 §1.2 在「每帧重画」的老体制下只省 16 ms，现在体制变了，重新量。
3. 亮度 ≠ 1 时 `ctx.filter` 逐片走滤镜层：改成先把片画进影像草稿画布、再带 filter 一次 `drawImage`。只在实测亮度 ≠ 1 明显更慢时做。

## 7. 坑清单（都踩过）

1. **`lastRebuildMs` 不能再单独当判据**——它是本任务书要治的东西本身。任何「便宜就直接重建」的分支必须看 `costEst`。

### 10.1 §1 复核：四条根因全部复现，但 §4.1 的探针口径要改

改动前（HEAD 963d185 + 只加读数、判定一行未动）实测：

| 根因 | 实测 | 判定 |
|---|---|---|
| ① 缩放期「便宜就同步重建」 | ① 50m+瓦片 10 帧 **10 次 `rebuild:fast`**，帧 [60.9, 2, 1.5, 122.6, 3.7, 3.8, 132, 4, 4.8, 85.9]；③ 10m 影像关 **10/10 `rebuild:fast`**，中位 116.5 ms、最大 284.4；② 10m+瓦片 5 次重建、最大 318.3 | 复现，且比任务书写的更重 |
| ② 慢速滚轮撞静止补建 | ① 8 格 × 150 ms 里 **8 格全是重建**（`fast` 或 `invalid`），单格最大 40.4 ms | 复现 |
| ③ 拖动中间停一下 | ① DPR 1.5 拖停三轮，**第 2、3 轮开头都是 `rebuild:invalid`**，帧 60.8 / 46.7 ms | 复现 |
| ④ 放大视角往外缩 | ① 从 t=0.45 缩 10 步：1 次 `rebuild:uncovered` + 6 次 `rebuild:fast`，帧最大 55.2 ms | 复现 |

**★ 与任务书不符的一条（照 §8.5 先改口径再继续）**：§4.1 说「重建之后排一个探针帧，量下一帧被顶住多久」。
实测**空 rAF 探针量不到**——连排三个空 rAF 全读 0～0.1 ms，而随后两个**会画东西**的帧读到 231 ms。
原因是光栅队列不会在一个「什么都不画」的回调上排队。改成：

- 探针口径 = 「重建帧起点 → 后面**头三个真正绘制的帧**的起点」各段间隔，逐段扣掉 `nominal` 后累加，
  再与 `lastRebuildMs` 取大（Chromium 切回同步光栅模式时后者自己就是 100+ ms，两种模式都盖住）。
  帧数取 3：顶住落在第 1～3 帧都见过（`6 / 0 / 231.5`、`185.2 / 0.2 / 30.6`、`1.7 / 0.2 / 45.3` 三种都实测到）。
- 静止时后面没有帧可数 → `armProbe` 补几帧**逐像素相同的重绘**把账结掉。副作用是好的：
  那份顶住从「用户下一次手势的第一帧」挪到了静止期。
- `nominal` = 非重建帧的帧间隔滚动最小值，钳 [4, 20]（验证台无 vsync 实测落到下限 4；真机会跟到刷新周期）。

**★ 判据比任务书更保守（两处）**，因为探针会漏读：
迟滞从「连续两次 < 8 ms」改成「**连续三次 < 8 ms 且衰减最大值（`max(新读数, 旧值×0.6)`）也降到 8 以下**」；
理由是同一视角连着量三次会出现 `45 / 35.4 / 1.3` 这种漏读，单次读数不足以翻档。判错成「贵」只是多走一次
缩位图（缺省路），判错成「便宜」就是手势里插一次整份重建——两头刻意不对称。

### 10.2 Stage 1 落地与自身发现的三个坑

按 §4.1 → §4.2 → §4.3 → §4.5 → §4.4 做完，另有三处任务书没预料到的：

1. **回退快照一张都留不下**（§4.4 的判据写错了层）。§4.4 说「重建时若旧快照的内容代与新的相同就留」，
   实现若按 `staticValid` 判就永远留不下——静止补建（`rebuildAtRest`）正是先把 `staticValid` 置假、
   再走进 `renderStaticLayers` 的那一条。改成记 `snapGen`（烘这张时的内容代），判 `snapGen === staticGen`。
2. **瓦片到货把回退快照清光**。`onTileReady` 原本走 `invalidateStatic`（= 内容变 → 清 fallbacks）。
   放大之后瓦片陆续到货，正好把「缩回去时垫底的那张全图」清得一张不剩，于是缩回全图又露空环。
   改成走 `rebuildAtRest`：瓦片到货只是**多了几片影像**，不是换了内容；少几片影像的回退快照垫在下面完全够用。
3. **慢滚里仍漏进 2 次补建**（① 50m+瓦片，其中一格 62 ms）。两个原因：
   (a) `idle = clamp(2.5 × cost, 110, 350)` 对 cost ≈ 25 ms 的档算出 110 ms，比滚轮格间隔（150～300 ms）还短。
       改成**热窗口与补建阈值分家**：贵的视角热窗口拉到 `ZOOM_RUN_MS = 350`（整串滚完之前一次都不补建），
       便宜的视角照 `idle`（那一次重建本来就 < 8 ms，落在格间也不顶谁）。
   (b) **手势之前**挂上的瓦片去抖定时器到期时不再判热。改成到期时**再判一次** `gestureHot()`，热就转 `tilesDirty`。
4. **平移量化要带残差**。直接 `round(v×dpr)/dpr` 会把「每次只动零点几个设备像素」的连续小位移整段吃掉
   （高 DPI 触控板给的 `clientX` 是小数，光标走了图一动不动）。改成把量化残差留到下一次一起补上，
   残差恒 < 1 个设备像素。单测里 200 次 ±0.37/−0.11 px 累加逐 DPR 验过。

调度口径的纯函数（视角类分档、迟滞、量化、快照摆放与覆盖判定、回退挑选、evenodd 裁剪矩形）拆到

1. **视图要从 A 读出来喂给 B**。当前版的静止重建把 `tx/ty` 量化到整设备像素，基线版不量化；

   两边都对却差 0.07% 的像素（最大 6/255）。逼过之后比的才是 §4.2 写的那个口径 ——
   「blit 出来的静止画面 = 在同一个量化后的视图上现画一遍」。
3. **导出闸的视图同步要排在【丢掉的那一张之后】**。`exportRender` 末尾会 `staticValid = false` +
   `requestDraw()`，当前版随后的那次静止重建才把 `tx/ty` 量化；在它之前同步，B 拿到的是量化**之前**
   的视图（实测 robinson 所见即所得差 16～101 字节）。
4. **基线副本的 URL 只能运行时拼**。写成字面量 `import`，副本删掉之后 vite 的 import-analysis 让整个
   `main.js` 返回 500；写成非字面量表达式，浏览器按页面 URL 解析成 `/src/...`，而 vite 的 root 在
   `.imgharness` 下 → SPA 兜底返回 index.html →「Failed to fetch dynamically imported module」。
   现在从**已被 vite 改写过**的那条资源 URL（`performance.getEntriesByType('resource')`）上摘
   `/@fs/` 前缀，取不到再退回相对路径。§3 里那句「两种写法都能用」不成立，已按此更正。

### 11.1 ★ 必修：有余量的视角在静止时【无限循环重建】（`draw()` 2417 行）

```
if (mode !== 'rebuild' && (!pl.exact || !pl.covers || pl.dx || pl.dy || tilesDirty)) scheduleRebuild()
```

`pl.dx = rx − rec.mx`：快照带余量（`snapMxDev > 0`，即任何放大视角、或全图平移出画布之后）时，
**没动过的 blit 也有 `dx = −mx ≠ 0`** → 每一帧 blit 都 `scheduleRebuild()` → idle 到期 `rebuildAtRest` → 重建 →
探针催 3 帧 blit → 又 `scheduleRebuild()` → 循环，周期 = `idleMs`。实测：

- 全图 + 平移 12 px（余量 64）静止后：`rebuild:invalid` 每 300～400 ms 一次，2.5 s 内 5 次，每次 10m 全图 ≈ 110 ms 光栅
  （时间线 372 / 673 / 1080 / 1473 / 2222 ms，各跟 2～3 帧 blit）；
- 放大 t=0.3（余量 346/194）静止：2.5 s 内 42 帧 blit（重建帧被探针帧立刻盖掉、4 ms 轮询只看到 blit），周期 ≈ 130 ms；
- 对照：全图不动（余量 0）静止 2.5 s：0 帧。

后果：只要不在全图视角，软件闲着也在以 3～8 次/秒整份重建 + 光栅，GPU 常驻忙、笔记本风扇与电池遭殃，
且用户任何时刻起手都有概率撞上一次重建的光栅。

**修法**：`placeSnapshot` 多返回一个 `moved = (rx !== 0 || ry !== 0)`（缩位图分支恒 true），判定改用 `pl.moved`，
不再看 `dx/dy`。**可选**：`snapMxDev === 0 && snapMyDev === 0 && pl.covers` 时（世界整个在画布里）连 `moved` 也不补建 ——
Phase 1 §10.3 的逐像素闸早已证明全图视角 blit 与现画差 0；按闸决定。

**验收探针** `rest2d`：给 `__staticStat` 加单调计数 `drawSeq / rebuildSeq`（轮询会漏帧，计数不会），
在【全图 + 平移 12 px】【t=0.3】【t=0.45 + 拖 200 px 松手】三个视角静止 1 s 后再数 2.5 s：**`rebuildSeq` 增量 = 0、`drawSeq` 增量 = 0**。

### 11.2 ★ 必修：热态到货的瓦片仍按【内容作废】收（`idleFire` 558 行）

```
if (tilesDirty) { tilesDirty = false; invalidateStatic() } else rebuildAtRest()
```

与 §10.2.2 自己的结论矛盾：瓦片到货只是多了几片影像，走 `invalidateStatic` 就 `gen++` 并清空回退。
实测（放大视角 `setSizes({})` 后冷请求瓦片、随即热态继续缩 6 步、瓦片在热态到货、静止）：`gen` 24 → **25**（应为 24），
`fallbacks` **0**（应为 1）。手势里到货这条路正是 §10.2.2 想护住的场景，目前只护住了「不热」那条。

**修法**：`tilesDirty = false; rebuildAtRest()`，两条路都不 `invalidateStatic`。验收：上述序列 `gen` 不变、`fallbacks = 1`、
随后缩回全图 `reason:fallback`。

### 11.3 ★ 必修：放大视角、没有回退时按住拖过余量 → 海色条跟着光标走（`draw()` 2409–2410 行）

`!pl.covers && !fb && !clsCheap(cls)` 时平移也走 `reason:'ocean'`。放大视角的类几乎永远判不成「便宜」（迟滞要连续三次 < 8 ms，
而 10m 中等视角一次 30～50 ms），于是：从存档恢复到放大视角（首次重建时没有更宽的旧快照可留）、或任何一次内容作废之后，
按住拖过 18% 余量就露出一条**纯海色、没有海陆线的条带**，随拖动一直变宽，松手后还要等 `idleMs`（未知类 350 ms）才补上。
实测 t≈5×（`setSizes` 清掉回退后）拖 40 帧 × 12 px：**21 帧 `blit:ocean`**。Phase 1 在这里是同步重建一次（30～50 ms 顿一下），
观感上「顿一下」远好过「一条空海跟着手走」。

**修法（Stage 1 内）**：**平移**盖不住且没有回退 → 一律 `doRebuild('uncovered')`（与 Phase 1 相同，每拖半个视口一次）；
`'ocean'` 只留给**缩位图**（缩小）那一支。
**根治（并入 Stage 2 §4.6）**：内容变了之后静止时，若没有任何回退能盖住整个世界，就用 **50m 档烘一张全图背板**
（≈ 3 ms，`rotLive` 降档的同一套机制、两档几何已按 §4.6 同时缓存）压进 `fallbacks` 当通用回退 —— 之后不论平移还是缩小都有东西垫，
11.3 的同步重建与 §4.4 的海色垫底都退成兜底路。这一条写进 Stage 2 的改动清单。

### 11.4 加固：`nominal` 会被同步 `draw()` 污染到下限，真机上「便宜」永远判不出来（2381 行）

`noteNominal(_tIn − lastDrawAt)` 拿**任意两次 draw 的间隔**取滚动最小值、只降不升。`resizeNow`（ResizeObserver、切侧栏、
换画质档）是同步 `draw()`，与同一拍里挂着的 rAF draw 间隔 0～3 ms → `nominal` 一次就钉死在下限 4。真机 60 Hz 上便宜的重建
后一帧 gap ≈ 16.7 → `rasterExtra ≈ 12.7 ≥ 8` → **所有类永远「贵」**，§4.1 的放大同步重建（清晰优先）在应用里根本不会启用。
验证台无 vsync 看不出这件事（本来就是 4）。

**修法**：`nominal` 只从 **rAF 时间戳**估：初始化时连排 6 个空 rAF 取相邻时间戳之差的中位数（约 100 ms 一次性），
`watchDpr` 触发与窗口重新获得焦点时重估；钳 [4, 20]。`draw()` 里不再 `noteNominal`。验收：验证台 `nominal` 仍为 4；
在 `__staticStat` 里暴露 `nominal` 供用户在 Electron 里读（应 ≈ 16.7 或 6.9）。

### 12.4 验证台的两个坑（本次踩到）

- **浏览器面板藏起来时 `setTimeout` 被 Chromium 节流**（链式计时器嵌套到 5 层后 1 次/分钟）：`_wait` 一个个 1 s 变 60 s，`rest2d` 跑了三分钟还在第一格。本次在页面里把 `setTimeout / clearTimeout` 换成 MessageChannel 驱动的计时器垫片（与 rAF 垫片同一思路）才跑完；已并入 `main.js`。
- **4 ms 轮询 `__staticStat` 会漏掉被探针帧立刻盖掉的重建帧**（放大视角一次重建只要 1～5 ms 同步）—— 只信 `drawSeq / rebuildSeq` 计数，别信轮询。
