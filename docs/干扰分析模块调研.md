## 0. 一句话

新开独立窗口「干扰分析」，把链路预算里长期靠手填的四路 C/I 变成算出来的：
**C/ASI（邻星）· C/XPI（交叉极化）· C/CCI（同频多波束）· NGSO 时变 C/I（CDF）**。
计算器只读不回填 —— 三个链路预算引擎一行不改。

## 1. 现状盘点

### 1.1 五路 C/I 全是手填常数

三个引擎共用同一套（[linkCalculator.js:773-828](../packages/core/utils/linkCalculator.js)、
[linkCalculatorNGSO.js:954-998](../packages/core/utils/linkCalculatorNGSO.js)、
[linkCalculatorRegen.js:55-91](../packages/core/utils/linkCalculatorRegen.js)）：

| 路 | 字段 | 默认 | 物理计算 |
|---|---|---|---|
| 上行 C/ACI | `aciUplinkFactor` | 30 dB | ✗ |
| 上行 C/ASI | `adjUplinkFactor` | 25 dB | ✗ |
| 上行 C/XPI | `xpolUplinkFactor` | 26 dB | △ 仅与 P.618-14 §4.1 雨致 XPD 合成 |
| HPA C/IM | `hpaIntermodFactor` | 24 dB | ✗ |
| 下行 C/ACI · C/ASI · C/XPI | `aci/adj/xpolDownlinkFactor` | 30 / 25 / 26 | ✗（XPI 同上） |
| Tpdr. C/IM | `xpdrIntermodFactor` | 21 dB | ✗ |
| **C/CCI** | — | — | **该路不存在** |

合成口径（后续所有集成的约束）：

```
C/T_i = (C/I)_填 + k + 10·lg(B_转发器)
上行总 C/T = −10·lg( Σ_j 10^(−C/T_j/10) )      ← 热噪 + 四路干扰线性并联
```

即所有 C/I 都定义在「占满整个转发器的名义载波」参考点上（瀑布表称「转发器参考口径」）。
弯管体制下上行干扰随转发器转嫁到下行，再生式改为上下行各自直接并联 —— 这两处口径正确，不动。

## 3. 算法

### 3.1 C/ASI —— GSO 邻星干扰

**拓扑角（不是经度差）**

```
θⱼ = arccos( (S₀−P)·(Sⱼ−P) / (|S₀−P|·|Sⱼ−P|) )
```
P = 站点 ECEF，S₀ = 期望星、Sⱼ = 干扰星（GEO 圆轨道，r = 42164.17 km，赤道面）。

拓扑角**恒大于**经度差且永不相等 —— 站点比地心离同步弧更近，看过去被放大，
倍率在星下点最大（42164/35786 ≈ 1.178），随离轴变远而减小（实测值）：

| 站 | 期望星 / 干扰星 | 经度差 | 拓扑角 | 倍率 |
|---|---|---|---|---|
| 北京 39.9°N 116.4°E | 110.5 / 113°E | 2.500° | **2.810°** | ×1.124 |
| 赤道 110.5°E 星下点 | 110.5 / 113°E | 2.500° | **2.945°** | ×1.178 |

解析校验：星下点处 `2×42164×sin(1.25°)/35786 = 2.945°` ✓

离轴增益斜率是 25·lgφ 量级 —— 2.5° 处 0.31° 的角度误差 = 1.2 dB 鉴别度误差，直接落进 C/ASI。
现有硬编码 `deltaTheta = 2.5` 是经度差近似，**用它算 C/ASI 会系统性偏乐观**；新模块不沿用。

**下行**

接收系统各项（FSL、G/T、噪温）在 C 与 I 之间抵消，只剩天线鉴别度 —— 这正是 SATSOFT
那个对话框只要「经度 + EIRP 密度 + 开关」三个输入的原因。

```
(C/I₀)ⱼ = [EIRP_c − 10lg(B_c) − eⱼ] + [G_rx(0) − G_rx(θⱼ)] − [FSL₀ − FSLⱼ] + Xⱼ
C/I₀    = −10·lg( Σⱼ 10^(−(C/I₀)ⱼ/10) )
```
- `G_rx(θ)` = 现有 `calculateITU465OffAxisGain`（AP8 + S.580 包络）
- `eⱼ` = 干扰星下行 EIRP 密度 dBW/Hz（三通道任取）
- `Xⱼ` = 极化折减：同极化 0；反极化取 XPD（默认按 ITU-R S.736 给，可手改）。**默认开启，可关**

**上行**

不要求用户掌握干扰地球站的具体参数 —— 用 **S.524-9 离轴 EIRP 密度掩模**作干扰源上限
（行业标准做法，代码已有，直接复用）：

```
Iⱼ_den   = S524_mask(θⱼ, f_up) − 10lg(参考带宽/1Hz)
(C/I₀)ⱼ = [P_本站 + G_tx(0) − 馈损 − 10lg(B_c)] − [Iⱼ_den + ΔG_sat] + Xⱼ
```

**附赠：施扰侧 ΔT/T（RR AP8）**

给出本网对邻网是否触发协调门限的判据 —— 对做 ITU 协调是日常刚需。
（原文曾写「`txSidelobeEIRP` 引擎已在算，只差 ΔT/T 那一步」：那个出参由假角度 deltaTheta 派生，
已于 2026-08-07 删除，本模块须自己按真实几何的离轴角算施扰侧旁瓣 EIRP 密度。）

### 3.2 C/XPI —— 交叉极化

三源功率合成：

```
1/XPI_tot = 1/XPI_卫星 + 1/XPI_地球站 + 1/XPD_雨
```

| 源 | 取法 |
|---|---|
| XPI_卫星 | GRD `pol:'P1/P2'` 在站点位置逐点实测 —— 平台独有资产 |
| XPI_地球站 | 天线极化纯度：直接填 XPD / **由轴比换算**（圆极化，`20lg((r+1)/(r−1))`）/ 由实测共/交极化电平相减；另可叠加**极化对准误差** τ（线极化，`−20lg(tanτ)`）与之功率合成 |
| XPD_雨 | P.618-14 §4.1，**已实现** |

> **边界必须在 UI 上写明**：GRD 给的是卫星天线的极化鉴别度，不是端到端 XPI。
> 把它当全部 XPI 会偏乐观。

地球站那一段只能由用户给，但**「给」不等于「填一个 XPD 数」**：手里拿到的是规格书上的轴比、
测试报告上的两条曲线、或对星时的极化对准误差，逼用户先自己按计算器再填个数进来，既容易按错、
也把「这个数怎么来的」丢了。故 `ciXpi.resolveXpd()` 统一收三类形状（数字 / `{db,source}` /
`{mode,...}` 描述子），三段都能用任一种给法，换算与算式留痕全在引擎里做——
渲染端不重写公式（`ci:xpiTerm` 一个 IPC 往返换掉一份必然漂移的镜像）。
校验点：AR 0.55 dB ↔ XPD 30.0 dB，与「主瓣内 XPD ≥ 30 dB」这条常见入网要求互为表里。

### 3.3 C/CCI —— 同频多波束

```
C/CCI(点) = G_服务波束(点) − 10·lg( Σ_同色波束 10^(G_k(点)/10) )
```

两处扩展：

1. **`grdSampler` 加 `sampleAll`** —— 现有 `sampleMax` 只回多波束最大值
   （[grdSampler.js:239](../packages/core/utils/grdSampler.js)），C/CCI 需要逐波束
2. **频率复用着色** —— 波束合成模块目前无 color 标注。新增「复用方案」：
   **4色 / 3色 / 7色**预设 + 手工指派

> ⚠️ **工程要点：C/CCI 的合成必须在主进程完成，只回 C/CCI 一个数。**
> 场图是几千格 × 几十波束，把逐波束值搬过 IPC 会撑爆消息体。
> `electron/services/grd.js` 加 `sampleCci(req)` 入口，内部调 `sampleAll` 后当场合成。

### 3.4 NGSO 时变 C/I → CDF

```
for t in [t₀, t₀+T) step Δt:
    S*(t) ← 选星策略（最高仰角 / 最长驻留）
    for 每个干扰星 i（同星座 + 其他 NGSO 星座）:
        θᵢ(t) = 地球站视角下 S*(t) 与 Sᵢ(t) 的夹角
        Iᵢ(t) = EIRPdenᵢ + G_rx(θᵢ) − FSLᵢ + Xᵢ        ← G_rx 走 ITU-R S.1428（新写）
    C/I(t) = C(t) − 10·lg(Σᵢ 10^(Iᵢ/10))
→ 排序得 CDF → 报 C/I(p%)；识别 in-line 事件（θ < 主瓣宽度）的时段与占时比
```

**性能设计（三级，全部照搬可见性分析）**

1. `orbitCanReach` 几何粗筛，只留轨道能到本站纬度的星
2. 逐时刻仰角门限二次筛，只对可见星算
3. 步长自适应，in-line 附近加密（复用 `eventWindows` 窗口细化思路）
4. 计算量预估拦截 + 分帧异步 + 取消令牌 + 进度文案

**口径分离**：干扰 p%（几何统计）与雨衰 p%（传播统计）物理独立，UI 上分开标注，
不做隐式合并。

## 6. 三个必须守住的口径

1. **θ 是拓扑角，不是经度差。** 见 §3.1。
2. **C/I 是带宽不变量**（干扰源与载波谱密度形状一致时）—— 这是「只看不回填」仍然对得上
   引擎那套转发器参考口径的物理依据。也正是本期不做 C/ACI 与 C/IM 的原因：那两路与载波
   排布、转发器装载强相关，不满足这个条件。
3. **干扰与降雨的耦合。** 下行降雨 C/I 基本不变（同路径同衰减）；上行本站降雨 C/ASI 实打实
   恶化（本站信号衰减、外来干扰源不衰减）。现有引擎显式当作不变
   （[waterfallBuilder.js:550](../packages/core/utils/waterfallBuilder.js)）；
   新计算器给「晴空 / 雨中」两档，把差异摆出来。

6. 联调 + 对着 SATSOFT 逐项校对数值 + 出图口径核对

## 9. 实测发现（实现阶段，2026-07-26）

写代码时跑出来的、与原方案有出入的七件事。**下次动这个模块前先读这一节。**

### 9.1 S.1428-1 的系数不能凭记忆写

已按 ITU 官方 PDF 正文逐段核对。三处与常见记忆不符、抄错就是几 dB 的误差：

| 项 | 事实 |
|---|---|
| `Gmax` 常数 | `D/λ ≤ 100` 档是 **+7.7**，`D/λ > 100` 档是 **+8.4** —— **两档不同**，不能混用 |
| 大档 10–34.1° | 是 **34 − 30 lgφ**（掉得比 29−25lgφ 快），不是继续用 29−25lgφ |
| 远旁瓣平台 | 小档(20–25) 末段 **−5**；中档(25–100) 是 **−9 / −4 / −9**；大档(>100) 是 **−12 / −7 / −12**。三档各不相同 |

`D/λ < 20` 超出该建议书适用范围 → 返回 null，由调用方回退 AP8（已实现并测试）。

### 9.2 ★ S.1428 不是「一律比 AP8 低」—— 交叉点在约 37°

原方案里「AP8 峰值包络会系统性高估 NGSO 干扰」的说法**只对近区成立**。实测（D=1.2 m @ 12.5 GHz）：

| 离轴角 | AP8（峰值） | S.1428（平均） | 差 |
|---|---|---|---|
| 2–35° | 更高 | 低 1.5 dB | 近区确实是峰值偏保守 |
| 40–60° | −11.50 | −9.00 | **+2.5 dB** |
| 80–120° | −11.50 | −4.00 | **+7.5 dB**（溢出区） |

AP8 的远场底板（−3−5lg(D/λ)）是**设计目标值**，S.1428 的溢出平台是**实测统计**——真实天线在大角度上漏得比设计目标多。

**后果**：大星座的干扰星散布全天，多数落在 40° 以外，于是 **S.1428 给出的聚合 C/I 反而比 AP8 更低（更保守）**。
实测 16 星本座 + 36 星干扰座：中位 C/I **47.85（S.1428）vs 51.86（AP8）**，差 4 dB。
`patternKind` 两条都保留，就是为了让使用者能亲眼比一次。

### 9.3 ★ 上行 C/ASI 必须区分「监管上界」与「工程估算」

只按 S.524-9 掩模算，得到的数没法给工程用。实测（北京 4.5 m，110.5°E 对 113°E，θ=2.81°）：

| 口径 | 邻站离轴 EIRP 密度 | C/ASI |
|---|---|---|
| S.524 掩模（顶格发） | +27.78 dBW/40kHz | **6.9 dB** |
| 同类站对打（4.5m/40W/36MHz） | +0.76 dBW/40kHz | **36.9 dB** |

差 27 dB —— 真实站离限值还远得很。故 `uplinkCAsi` 加了第三种模式，且**默认走 peer**：

- `peer`（默认）把干扰站按具体天线建模（口径/功率/带宽/馈损），同一条 AP8 包络算旁瓣密度。工程估算用这个。
- `mask` 监管硬上界，卡协调门限用。UI 上已写明「不是运行值」。
- `explicit` 拿到对方实测数据时用。

peer 模式还会顺手核一下这座假想干扰站自己合不合规，超 S.524 就告警——那说明假设本身不成立。

### 9.4 ★ in-line 事件的采样混叠：会安静地报出「0 次」

最危险的一处，因为假得毫无征兆。1200 km LEO 过顶视角速度约 **0.33 °/s**；4.5 m Ku 天线主瓣 0.373°，穿越只需 **~1.17 s**。用 5 s 步长扫 24 h：

| 天线 | 主瓣 | 穿越时长 | 5 s 步长的粗扫结果 |
|---|---|---|---|
| 1.2 m | 1.399° | 4.37 s | 采得到，6 次/24h |
| 4.5 m | 0.373° | 1.17 s | **假报 0 次**，最差 C/I 也跟着假 |

看上去像「大天线更抗干扰」，实际是根本没采着。已实现三层防护：

1. `requiredStepSec()` 由干扰星轨道速率与主瓣宽算出所需步长，超了就**告警**并给建议值；
2. `refineInlineEvents()` 对候选时段**细步重扫**定出真实穿越（4.5 m 那例从 0 次变 1 次/天、时长 1.17 s，与理论值吻合）；
3. 结果里 `cdfAliasRisk` 明示：事件表已细化，但 **CDF 本身仍是粗步的**，尾部可能漏采——UI 上有醒目告警框。

**CDF 与事件表刻意用两套采样率**：CDF 要求时间上等权采样，混入细采样会把分布往细化区带偏；事件按时长报，不进 CDF 样本池。

### 9.5 拓扑角的放大倍率（正文 §3.1 已补实测值）

拓扑角恒 > 经度差且永不相等，星下点放大最大（×1.1782）。别按等腰三角形近似——那样偏 0.3 mdeg。

### 9.6 ✅ S.524 已统一 —— 引擎 C 频段错了 6 dB，已订正

按 **ITU-R S.524-9 (2006) 官方 PDF 正文逐条核对**。建议书**只覆盖三个频段组**：

| recommends | 频段 | φ₀ | A | 平台 | B | 底板 | 参考带宽 | 引擎原值 |
|---|---|---|---|---|---|---|---|---|
| 2 | 5.725–7.075 GHz（C） | 2.5° | **32** | **11** | **35** | −7 | 4 kHz | 26/5/29/−7 ✗ **低 6 dB** |
| 3.1 | 12.75–13.25 / 13.75–14.5 GHz（Ku） | 2.5° | 39 | 18 | 42 | 0 | 40 kHz | 一致 ✓ |
| 4 | 27.5–30 GHz（Ka） | 2.0° | 19 | −2 | 22 | −10 | 40 kHz | 一致 ✓ |

**处置**（2026-07-26）：

1. **C 频段订正 +6 dB**（A / 平台 / B 三项；底板 −7 本就对）。Ku 与 Ka **逐位不变**，已测。
2. **两个引擎的内联表合并到 `interference/patterns.js`** —— `linkCalculator.js` 与
   `linkCalculatorNGSO.js` 各内联过一份 ~300 行的频段 if 链（各 49 处赋值），分歧正是这么来的。
   两处各删 308 行、换成 20 行的共用调用，此后单一出处。
3. **φ < φ₀ 的钳位**：建议书原文是「at any angle φ which is 2.5° or more off-axis」——
   主瓣内**根本不设限**。故按 φ₀ 处连续钳住并置 `belowScope=true`；引擎旧实现的 `A+9` 无出处，已废。
4. **诚实标注**：S.524-9 不覆盖的频段（X / 10.7–11.7 / 17.3–18.4 / Q / V / 低C）数值沿用不动，
   但一律置 `authoritative=false` —— 它们是按邻近频段外推的工程值，UI 与报表**不得标成「ITU-R S.524-9」**。

**影响面**：C 频段 GSO/NGSO 链路预算的「ITU 功率谱密度门限」出参放宽 6 dB，
相应的 PSD 合规判定结果会变。这是订正，不是回归。

**另发现**：掩模在 φ=7° 处**建议书自身**有约 0.13 dB 的台阶（斜段 `39−25lg7 = 17.87` vs 平台取整成 `18`），
三个频段一致，是平台值取整数造成的，不是实现错。测试已按此放宽并单独钉住。

### 9.7 S.672 未实现（诚实空缺）

其官方 PDF 抓取连续失败，不凭记忆写系数。卫星侧增益的**主路径是 GRD 实测方向图**；无 GRD 时用 `gaussianSatBeam()` 兜底，该函数已在注释与返回值（`approx:true`）里明确标注**这不是 S.672**、仅主瓣内可信。要用参考图请先补 S.672。

## 11. 二轮修订（2026-07-26，用户反馈后）

### 11.1 ★ GRD 取 XPD 取出负数 —— 共极化分量认反了

现象：在本站取值得到 **−31.35 dB**。根因不是取值错，是**假设错**。

实测三份真实 GRD 在各自波束峰值处：

| 文件 | icomp | 10lg(P1) | 10lg(P2) | P1/P2 |
|---|---|---|---|---|
| CS10R 300_X02G_EIRP | 3 | 21.94 | **52.87** | −30.93 dB |
| EIRP_OK1 | 2 | 23.97 | **67.42** | −43.45 dB |
| to_Bj_EIRP_Cant_Beam | 2 | 4.18 | **38.45** | −34.27 dB |

峰值处共极化必远强于交叉极化 → **这些文件里第二个分量才是共极化**，与「icomp=3 时分量1=co」的
常见理解相反。各家工具写入顺序并不统一，**按 icomp 硬判必然踩坑**。

**修法**：`grdSampler.coPolIndexOf()` —— 共极化 = **波束峰值处占优的那个分量**。
物理上无可争议，且与文件怎么写、icomp 标几都无关。

**同时修掉第二个错**：原路径 `pol:'P1/P2'` 走 `sampleMax`，是在**各波束的比值里取最大**，
跟该点实际收哪个波束毫无关系。新增 `sampleXpd()` 取**服务波束**（该点共极化最强者）的共/交比。

修复后（CS10R，站点实测）：

| 站 | 旧法 | 新法 XPD | 服务波束 | 共 / 交 |
|---|---|---|---|---|
| 北京 | −31.35 | **31.89** | #8 | 52.8 / 20.9 |
| 上海 | −35.31 | **36.21** | #5 | 54.2 / 17.9 |
| 乌鲁木齐 | −37.02 | **41.09** | #7 | 53.5 / 12.4 |

不只是翻符号——服务波束选错时数值也不同。

### 11.2 天空图重做：默认「聚焦主轴」

原全天半球图上，C/ASI 的干扰星（θ 常 0.5°–3°）与期望星挤在图幅不到 2% 的地方，
「看着不真切」正源于此——90° 的画布画 1° 的事。

新增 `geometry.boresightOffset()`：切平面（gnomonic）投影，原点 = 天线主轴，
x 右 / y 上，模长恰为拓扑角（已测 |x,y| ≡ θ）。两个视图：

- **聚焦主轴（默认）** 量程按最远干扰星自动定，等离轴角环**逐环标出「离轴角 · 该处增益 · 鉴别度」**
  —— 把「θ 是多少」直接翻译成「鉴别度是多少」。环的档位（主瓣边缘 / φ₁ / φr / 工程刻度）
  与其上的增益全部由引擎给（`geometry.patternRings`），渲染端不复算方向图。
- **全天** 保留作方位参照。

### 11.3 C/CCI 覆盖场图

复用 `LbSurfacePlot`（世界底图 + 等值线 + Turbo + 拖拽缩放）。逐格合成在主进程完成，
只回一个标量场。实测 71×41 = 2911 格用时 22–39 ms。

物理自洽性实测（CS10R 11 波束，中国区）：色数越多 C/CCI 越好 ——
3 色中位 −4.0 dB → 4 色 −2.4 dB → 7 色 +0.4 dB；7 色下 2111/2911 格无同色波束、正确留白。
（数值偏低是轮转着色把空间相邻波束染成同色所致，正是 §3.3 已标注的缺省着色局限。）

### 11.4 接入软件既有星历

- **邻星搜索**（C/ASI）：`ci:geoNeighbors` 载入 `geo` 组、按**当前星下点经度**排序，
  按「与本星轨位的经度差」升序给出——最近的排最前，正是 C/ASI 关心的次序。
  倾角残余星（星下点纬度 > 0.5°）标「倾」，提示按赤道面圆轨道近似会有偏差。
  **EIRP 密度仍须手填**——那是邻网发射参数，任何星历里都没有。
- **NGSO 星座**（本星座与干扰星座都可）：`ci:groups` / `ci:loadGroup` 接 17 个星座组
  （Starlink / OneWeb / 北斗 / GEO …），与主窗口「星座」页同一份数据。
  Walker 参数模式保留，供手上只有设计参数、还没有 TLE 的方案比选。大星座用「取前 N 颗」限量。

### 11.5 上行 C/ASI 在掩模模式下偏低 —— 是口径不是 bug

掩模是**监管硬上界**（假设邻网每座站顶着限值满发），不是运行值，详见 §9.3。

### 11.6 ★ 星历接不上 —— 走错了数据源（首版 bug，已修）

现象：NGSO 与 C/ASI 的星座搜索全部失败，像是"没和主程序连上"。

**根因（两处叠加）：**

1. **主进程的 `groups[]` 永远是空的。** 整个 app 的星座数据实际走
   `omm.fetchCsv()` → CelesTrak **OMM CSV**（存 `csv_<组>.csv`），渲染端
   `viz/constellation/tle.js` 拿到 CSV 后**在渲染端自己建 satrec**。
   主进程的 `groups[]` 只有 `omm.load()` 才会填，而 `load()` 读的是另一个文件
   `<组>.tle`（3LE 文本）—— 那是历史遗留路径，app 正常使用下根本不写。
   于是 `omm.peek('geo')` 恒为 null。
2. **`load()` 取不到缓存时会把 `group` 改写成 `'sample'`** 再 parse，
   于是 `groups['geo']` 更不可能有值，且不报错——静默失败。

盘上实况（用户机）：`csv_geo.csv` / `csv_starlink.csv` … **17 组一应俱全**，
外加 `resources/omm` 的内置快照；只有 `guowang.tle` 与 `starlink.tle` 两个遗留 TLE 文件，
**没有 `geo.tle`** —— 这就是 GEO 邻星搜索必然失败的直接原因。

**修法**：`omm.satrecs(group, opts)` 走与 app 其余部分**同一条数据源** ——
`fetchCsv(cacheOnly)` → 用户缓存 / 内置快照择新者（`offlineBest`），无网也能用；
解析用 `customSats.parseOMMCsv`（与渲染端 `tle.js` 同源同结果，已提成模块级静态导出，
不必为一个纯函数去造实例）；解析后填进 `groups[group]`，`peek()` 与 `positions()` 一并可用。

实测（用户机当日缓存）：GEO 569 颗 / Starlink 10832 / OneWeb 651 / 北斗 53，
110.5°E ±8° 内搜到 41 颗邻星，最近的 CHINASAT 16 (SJ-13) 在 110.503°（Δ0.003°），
BEIDOU-2 G7 等三颗被正确标「倾」。

**顺带修掉两处相关问题：**

- **「取前 N 颗」改为等间隔抽样。** CSV 按 NORAD 号排（≈ 发射批次），取前 N 条会拿到
  同一批、同几个轨道面的星，几何上完全不具代表性（实测服务可用度 22% → 改后 67%）。
- **抽样偏差不再静默。** 只算 1/K 的干扰源，聚合干扰必然偏低约 10·lg(K) dB，
  **C/I 系统性偏乐观**。现由 `samplingFactor` 显式回传并出醒目告警
  （例：「OneWeb 从 651 颗中抽了 100 颗（1/6.5）——聚合干扰偏低约 8.1 dB，C/I 偏乐观」）。
- **组列表区分 `count` 与 `available`。** 前者是内存里的星数，后者是「本地有 CSV 缓存或
  内置快照」（只探文件不解析）。首版把两者混成一件，用户看到的全是「未载入」——
  其实数据一直都在盘上。现在显示「（本地有数据）」，选中即自动载入。

### 11.7 「逐站给定」算不出数（首版 bug，已修）

`uplinkCAsi` 的 `explicit` 模式读 `offAxisEirpDensityDbWPerHz`，但**界面上根本没渲染这个输入框**
（参数表只在 `uplinkMode === 'peer'` 时出现）。于是每条干扰源都因缺值被跳过 →
无有效源 → `ciDb = null` → 界面显示算不出。已补上该模式的输入表，并在缺值时给明确提示。

### 11.8 ★ 干扰几何图重做：画方向图，不是画环

首版只画「等离轴角环」，被指「看着不真切」。症结有二：

1. **环只能表达角度，表达不了增益。** 而 C/ASI 的物理全在后者 ——
   鉴别度 = 峰值增益 − G(θ)。看不到方向图的形状，就看不出干扰星为什么吃到那么多/那么少鉴别度。
2. **标签没做去重叠。** 几颗近轴星的名字直接钉在点上，糊成一坨（见用户截图）。

**改法：三个视图，默认「方向图」。**

- **方向图（`CiPatternPlot.vue`，默认）** —— 横轴离轴角（**对数**）、纵轴增益 dBi，
  把 AP8/S.580 包络画成一条**真实曲线**，干扰星落在曲线上并引垂线到横轴。
  这是 MATLAB antenna toolbox 的 pattern cut、也是 ITU 建议书里方向图的标准画法。
  三个刻意的选择：
  · 横轴取对数 —— 主瓣常在 0.2°、远旁瓣要看到 180°，跨三个数量级，线性轴会把整个主瓣压成一条竖线
    （正是环图看不清的同一个毛病）；
  · **右侧副轴直接标鉴别度**（峰值 − 增益），读图不必心算；
  · 标出 AP8 的结构角（主瓣半宽 / φ₁ / φr / 远场底板）—— 干扰星踩在哪一段，决定了鉴别度是几 dB。
- **极坐标** —— 把同一条 G(φ) 渲染成**绕主轴的径向色带**（56 档），即波束方向图的俯视图，
  路数同 STK 的天线增益等值图；干扰星叠在上面，看得见它踩在主瓣还是旁瓣。
- **全天** —— 保留作方位参照。

**标签去重叠**：方向图里按增益排序后垂直顺次推开、超出则加引线；极坐标里标签统一排在右列、
逐条引线连回点上。两处都实测无重叠。

引擎新增出参：`geometry.patternCurve`（0.01°–180° 对数采样 401 点）与 `geometry.patternMarks`
（AP8 结构角及其增益）。**渲染端不复算方向图** —— 复算必与引擎漂移。

### 11.9 ★ NGSO 性能重做：步长 100s 卡死的根因 + 可见性掩码

**卡死根因**（用户实测复现）：in-line 细化的候选门限是 `max(主瓣, 视角速度×步长)×1.2`。
步长 100 s 时 = 0.33×100×1.2 ≈ **40°** —— 几乎每个时刻都成了候选，窗口合并成整条时间轴，
再按 0.87 s 细步重扫 24 h ≈ 十万样本 × 全部卫星，而 `finalize()` 是同步的 → 界面锁死。

**修法三件**：
1. 细化加**硬预算**（按传播次数 1.2e6 给，不按样本数——每样本的传播量随星座规模变，按样本数
   定预算星多时墙钟仍会膨胀）。预算内**按最近离轴角升序**挑最有希望的候选，不是按时间砍尾。
2. 丢弃量如实上报（`inlineDroppedWindows`）：「事件次数是下界，不是全部」。
3. 门限远大于主瓣时标 `inlineDegenerate`：粗扫已分辨不出穿越在哪，事件表仅供参考，并给降步长建议。
实测：步长 100 s 从卡死 → **78 ms**（测试锁住 <20 s）。

**可见性掩码**（每时刻只算可能露头的星）：

⚠ 第一版用**拓扑角速度**（0.68°/s）定粗步余量，粗步被逼到 37 s，掩码自身的传播量吃掉全部收益
——实测反而慢 9%~74%。症结：拓扑角速度是被站址放大过的量；判据必须建在**地心系**上：
`可见 ⟺ 地心张角(站,星) < γ(ε)+余量`，γ(ε)=acos((Re/r)cosε)−ε，余量=(轨道角速度+地球自转)×粗步。
地心角速度只有 ~0.063°/s（慢一个数量级）→ 粗步可取 270 s，掩码开销降到主扫的 ~4%。

实测（Starlink×OneWeb 真星历，i7 台式机）：
| 规模 | 优化前 | 优化后 |
|---|---|---|
| 600 星 × 12h/10s | 1495 ms | **723 ms** |
| 1850 星 × 12h/10s | （无法完成量级） | **1420 ms** |
| 2650 星 × 24h/10s | — | **2837 ms** |
| 1850 星 × 12h/100s | **卡死** | **820 ms** |

**正确性红线**：真 A/B（`_noScreen` 测试开关）逐项比对——样本数、中位、最差、四档分位
全部一致到 1e-5（北京/新加坡/北极三站型）；热路径的标量化改写与 geometry.js 通用函数
比对差 ~2e-6 dB = Float32 存储精度。全部锁进测试 ⑦（186 项）。

**热路径三处**：站址 ECEF/ENU 基提到循环外（原每星每时刻重算+分配临时数组，占传播的 60%）；
离轴角由两条已归一化 LOS 直接点乘（省掉 topocentricAngle 的重复计算）；FSL 频率项预算。

### 11.10 选了星座就不再填根数

`loadGroup` 回传 `stats`（由星历逐星反解）：星数 / 高度 min–max–中位 / 倾角范围 / 周期 /
**倾角主壳层**（1° 分箱取前三，Starlink 的 53°×5098 + 43°×3628 + 97°×1331 一目了然）。

### 11.11 ★ 上行也要有自己的干扰几何图；极坐标与全天两个视图删除

**问题**：「干扰几何」那张图画的一直只是**下行** —— 本站接收天线的方向图切面。
上行没有图，而上行恰恰是三种干扰源模型（对等站 / S.524 掩模 / 逐站给定）差 27 dB 的那一路，
只给一列数字看不出这个差是怎么来的。

**为什么不能拿下行那张图凑**：施扰者换了人。下行是「干扰星朝我发，我这面天线在那个角度上给多少增益」；
上行是「**邻网的发射站**朝它自己的星发、旁瓣泼进本星」——用的是**它的**天线、**它**看到的夹角
（非共址时与本站看到的拓扑角不是一个数，实测北京 2.8104° vs 广州站 2.8971°）。两件事，两张图。

**新增 `CiUplinkPlot.vue`** —— 纵轴取 **dBW/Hz 而不是 dBi**：三种源模型只有在「离轴 EIRP 密度」
上才对得起来（掩模模式根本没有天线，建议书给的就是密度上限）。统一到密度轴后一张图读三件事：

- **红虚线 = S.524 掩模**（监管天花板）。φ<φ₀ 段建议书本就不设限，画成点线并单独标 —— 画实线会
  让人以为主瓣区也有这么一条限值。掩模在三种模式下都画：它是那条天花板，不是某一种模式的私有物。
- **实线 = 对等站曲线**（主轴密度 − Gmax + G(φ)）。与天花板的落差就是 §9.3 那 27 dB，
  从「一列数字」变成图上一眼可读的一段距离。同参数的对等站合成一条曲线，异参数各一条。
- **水平线 = 本站上行 EIRP 密度（即 C）**，**它到落点的垂直距离就是该源的 C/I**，右侧副轴直接标出来
  —— 与下行图右轴标鉴别度是同一套做法。
- 落点若还吃了卫星鉴别 / 极化 / 频谱重叠，就从曲线上的**原始密度**（空心圈）画一段竖虚线落到
  **等效密度**（实心点），那一段的长度就是这三项一共给了多少 dB。

**钉死这张图的不变式**（已进测试）：`ciDb ≡ ownDensity − effectiveDensity`，逐源精确到 1e-12。
不成立的话右侧那根副轴就是骗人的。掩模模式下落点必须**恰好落在掩模线上**，也已断言。

**删掉两个视图**：**极坐标**（绕主轴的径向色带）与**全天**（天空半球）。理由与 §11.8 判环图死刑
是同一条 —— 它们只能表达角度、表达不了增益，而 C/ASI 的物理全在增益上；全天半球上这几颗星
还与期望星重合成一点（§11.2 当年就只把它留作「方位参照」）。随之删掉的还有
`geometry.boresightOffset()`（切平面投影，只为极坐标视图存在）与出参 `boreXDeg` / `boreYDeg`。
全天视图携带的唯一有用信息——期望星仰角——改由结果区 KPI 直接给出。

**两个踩过的坑**：

- **横轴下界不能只看最近的干扰源**。共址邻星（如 CHINASAT 16，Δ0.003°）会把对数横轴拉到 0.0005°，
  拉出三个**一条线也没有**的空白数量级（曲线自身只采样到 0.05°）。改为**不越过曲线的采样下限**，
  落在下限以内的源钉在左边缘 —— 方向图在主瓣内本就平，钉过去几乎无误差，真实角度由标签给出。
- **角度不能写死两位小数**。0.0034° 会印成「0.00°」，一个恒等于零的读数比不写还糟：它把
  「贴着主轴、对方几乎是对着我的星在发」误读成「就在主轴上，无需分辨」。改按量级给小数位
  （≥10° 一位 / ≥1° 两位 / ≥0.1° 三位 / 更小四位），下行图同步改。

### 11.12 ★ 删掉常驻侧栏 —— 「公共上下文」其实并不公共

原布局是「左侧公共上下文（本站 / 收信链 / 发信链 / 本链路载波）+ 右侧当前模式」。
用户反馈这条侧栏「没啥用，容易产生误导」。核对四种模式实际吃进引擎的量，反馈成立：

| 模式 | 真正用到的侧栏字段 |
|---|---|
| C/ASI | 全部（站址 + 收信链 + 发信链 + 载波含轨位与上下行极化） |
| C/CCI | **一个都没有** —— 取值点表自带经纬，场图自带经纬范围 |
| C/XPI | **只有站址经纬** —— 供 `grdSampleXpd` 取那一格 |
| NGSO | 站址 + 收信链 + 载波（EIRP / 带宽 / 下行极化）；**不吃轨位与发信链**（期望星是星座，只算下行） |

即四种模式里有两种几乎不用它，另一种用一半。常驻侧栏等于请人填一堆对当前页毫无作用的格子 ——
更糟的是填完还以为结果受它影响（在 C/CCI 页改「EIRP dBW」，C/CCI 一个数都不会变）。

改法：**侧栏整条删除，字段按页坐进各自的输入区**，逐项按模式开合。

- C/ASI · NGSO：页首一条「本站与本链路」输入带（`.ci-band`），四组 / 三组横排，
  组内是读数表式的两栏（标签左、值右对齐 104px），与链路预算工作台的 `.es-f/.es-l/.es-i` 同一手感。
  NGSO 页那条带下面加一句注脚，说明本页为何没有「卫星轨位」与「发信链」——
  少掉的格子要有人交代，否则换页找不着东西比多摆几个格子更烦人。
- C/XPI：站址两格坐在「在本站取值」按钮旁边，配一句「与另两页同一座站」。
- C/CCI：什么都不加。

`site` / `carrier` 两个 reactive 一字未动（三页共用同一座站，改一处另两处跟着变，这是要的）——
**删的是常驻的壳，不是状态**。

**一个布局细节**：输入带的网格轨道写死上限 `minmax(200px, 232px)`，不写 `1fr`。
侧栏一删主区宽出 250px，再用 `1fr` 会把多出来的宽度全灌进标签与值之间的空当，
一行读数拉成两头见不着的横幅。宽屏多出来的宽度宁可空在右边。

### 11.13 ★ 上行几何图的三处返工（用户实测截图）

用户实测那一幕：北京站 + 五颗邻星（拓扑角 0.284° / 0.717° / 2.23° / 2.41° / 2.51°），
**逐站给定**模式、五条都填 −48 dBW/Hz。截图上五个落点严丝合缝叠在同一高度，标签一路往下堆，
压到横轴刻度与轴名上糊成一坨。逐项查下来：**数是对的**（都填同一个密度，C/I 当然都是 39.6 dB），
坏的是图。三处返工：

**① 标签推开必须有边界（首版真 bug）。** 原逻辑只会 `labelY = max(y, last + 11)` 一路往下推，
没有下界。落点同高时（逐站给定把每座站都填成同一个密度，这在申报数据里很常见）整叠必然溢出绘图区。
抽出 `src/ci/ciPlotLabels.js` 两张图共用：

- 推完把整叠移回框内（先按下溢上移、再按上溢下移；叠高本身装不下时改为**均分压行距**，宁可挤也不出框）；
- 同高的点按**横坐标**排序再推 —— 只按纵坐标排，引线会互相交叉；
- 被推开的标签**排成一列**（各自贴自己点右边会得到参差不齐的左边缘，密集时更难读），
  列的横坐标还要保证最宽那条不越右边界；
- 孤点若靠右放不下，标签翻到点的左侧（`text-anchor=end`）。

SVG 里没有廉价的文字测量（`getBBox` 要先上屏），故宽度按字符估：CJK/全角约等于字号、西文约 0.56 字号，
估偏大一点没坏处。11 项断言锁死「不出框 / 不重叠 / 不越右界 / 单点不位移」（测试 ⑧）。
**下行图同步换成同一套** —— 两张图在密集时表现必须一致。

**② 没有实线时要说清为什么。** 掩模与逐站给定两种模式本就没有对等站曲线，
读者看到一条红虚线加几个孤零零的点，第一反应是「图没画全」。现按模式给一句：
逐站给定 → 「落点是你直接填的密度，该读的是它到红虚线的距离＝申报值离 S.524 天花板还有多少余量；
几座站填同一个数，落点自然同高」；掩模 → 「干扰源模型就是那条红线，落点必定在线上」。
图例也补上「干扰源落点」一项。

**③ ★ 掩模模式在 φ<φ₀ 内失效，原来是静默的（引擎缺陷，已修）。**
S.524 对 φ₀（Ku/C 为 2.5°、Ka 为 2.0°）以内**根本不设限**，`s524OffAxisEirpDensity()` 早就
返回了 `belowScope` 标志、值取 φ₀ 处的钳位 —— 但 `uplinkCAsi()` 从来没读过它。后果：
**轨位挨得近的邻星会得到一模一样的干扰密度、一模一样的 C/I**，看着像算错了，其实是掩模模型在
这个角上不成立。同一组五颗星走掩模模式，四颗在 φ₀ 以内、C/I 全是 8.6 dB。
现逐源出告警 + 出参带 `maskBelowScope`，图下方汇总点名，落点 tooltip 也标。
GEO 邻星间隔本就常在 2°–3°，**这个静默区正好压在最常用的工况上**。

**顺带**：`fmtAng()` 按量级给小数位（≥10° 一位 / ≥1° 两位 / ≥0.1° 三位 / 更小四位）。
原来写死两位，0.0034° 印成「0.00°」—— 一个恒等于零的读数把「对方几乎对着我的星在发」
误读成「就在主轴上，无需分辨」。

### 11.14 ★ NGSO 星座下拉：「我的卫星组」选了没反应、「自定义星座」根本没有（用户反馈，已修）

现象（用户原话）：「NGSO 时变中，选择星座时星座组和自定义还是没法选择」。
编目星座那一段一直是好的 —— 恰恰是这个"只坏一半"的表象把根因藏了很久。

**根因一（真 bug）：Vue 的响应式代理过不了 IPC 的结构化克隆。**
`satGroupIds` 当时是 `ref({})`，于是 `satGroupIds.value['sg:x']` 拿到的是 **reactive 代理数组**，
被原样塞进 `loadGroup(key, online, satIds)` 的入参。Electron IPC 走 V8 的结构化克隆，
**代理一律拒收**，`ipcRenderer.invoke` 当场抛 `An object could not be cloned.`；
而 `ensureGroup` 只有 `try/finally` 没有 `catch`，异常成了没人接的 promise rejection ——
界面停在「载入星座「筛选 tianqi」…」再没有下文，控制台之外一个字都不给。计算那条路同样当场废掉。
**编目星座之所以没事，只是因为它的 `satIds` 是 `undefined`**（可克隆），故障看着像「只有我的组坏了」。

实测（真 Electron，非浏览器模拟）：

| 入参 | `ipcRenderer.invoke` |
|---|---|
| `new Proxy(['44314',…], {get,set})`（≡ Vue reactive） | `ERR An object could not be cloned.` |
| `['44314',…]`（纯数组） | 主进程收到数组 3 项 |

修法：`satGroupIds` / `ccSats` **退出响应式系统**（界面一个字都不用它俩，纯数据没理由进 reactive），
`ngsoPayload()` 出 IPC 前一律现造纯对象/纯数组，`ensureGroup` / `estimateNgso` / `ngsoStart` 补 `catch`。
同一类隐患顺手扫掉：`grdSampleCci` 的 `coloring: cci.coloringOverride`（手工指派颜色后一算就炸）改浅拷贝。
**教训：凡是要过 IPC 的东西，出发前必须是纯数据 —— 本模块其余 payload 一直用 `.map(s => ({…}))`
现造，唯独这两张表是直接给的，就漏在这里。**

**根因二（功能缺口）：用户说的「自定义」是「自定义星座」，那一段压根没接。**
平台里"自定义"有两样东西，只接了其中一样：

| 叫法 | 存哪 | 谁在用 | 当时状态 |
|---|---|---|---|
| 自定义**星历** | 主进程 `custom.json`（文件管理导入的 OMM/TLE） | `ci:groups` | 已接 —— 但该机器一条都没导入，那一段永远是空的 |
| 自定义**星座** | 渲染端 `constellation3d/customConsts`（星座页 Walker 生成器） | 无 | **没接** |

现按 `cc:<id>` 接入：渲染端用**同一份** `walker.js/generateConstellation` 展开成逐颗经典六根数、
带上 `resolveScenarioEpoch` 的场景历元（与星座3D 页、NGSO 链路预算搜索池同源，绝不在主进程另写一遍放置公式），
引擎新增 `source:'elements'` 分支按 `type:'elements'` 建 satrec。参数不合法的座用向导那把尺子
（`validateWalker`）挡掉 —— 否则 `generateConstellation` 会兜底出一颗高度 0 的星。
测试 ⑨ 锁死：24/6/1 展开 24 颗、周期对解析解、第二面 RAAN=60°、等间隔抽样、空座报错。

**根因三（交互）：空的段静默消失 + 列表只在 mount 取一次。**
原来 `items` 为空的段直接 `filter` 掉，用户看到的就是"没有这一段" —— 既看不出该去哪儿建，
也分不清是没建还是坏了。现四段常在，空段给一条灰的说明项（「无 —— 在「星座」页用 Walker 生成器建」）。
又因为干扰分析是**单例窗口**（关掉才会重新 mount），开着它去主窗口建的组永远进不来，
而「联网刷新」按钮偏偏要求先选中一个 —— 死锁。现补：`storage` 事件（同源另一窗口写 localStorage
即刻同步）+ 窗口重获焦点重读 + 一个常驻的「刷新列表」按钮。
