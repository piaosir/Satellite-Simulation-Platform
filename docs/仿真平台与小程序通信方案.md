## 0. 结论

**可行，且比预想省事——因为两侧本来就是同一套字段名。**

平台的链路预算引擎是从小程序移植过来的，`satParams` / `linkParams` 的字段名两边**逐字相同**
（`sfdRef` `BOi` `BOo` `G_Ts` `rxEIRP` `rxAntennaNoiseTemp` `uplinkAvailability`…）。
所以「发送链路配置」不是造一套翻译层，而是**把平台的库引用摊平回扁平表单**——
`src/linkbudget/params.js` 的 `buildParams()` 已经在做这件事，只是它多做了一步引擎入口换算
（见 §3.4 的坑 1），导出必须绕开那一步。

三件事的难度排序：

| | 难度 | 主要成本 |
|---|---|---|
| 通道（一条密钥通道送三种载荷） | 低 | 已有 COS 中转，扩 `kind` 即可 |
| 链路配置发送 | 中 | 字段同名，但有 5 处口径差必须显式处理 |
| 频率计划发送 + 小程序看图 | 中高 | 小程序端全新页面；关键决策是**不在小程序重算版式** |

## 1. 现状盘点

### 1.1 已有通道（可直接复用）

2026-07 落地的「发送到小程序」（GXT 覆盖快照）已经把整条路打通：

```
平台 3D 页 buildMiniappSnapshot()
  → IPC share:gxtSnapshot
  → electron/services/share.js  putSnapshot()      PUT updates/gxt/<KEY>.json
  → 返回 8 位密钥（字母表 A-Z2-9，去掉 I L O 0 1）
小程序 输入密钥
  → cloudfunctions/importGxtSnapshot                https.get COS 公读直链
  → 内联返回 { success, data, fileID, meta }
  → 卫星覆盖页合并为一个波束、分键落 localStorage
```

关键设施与约束：

- **桶前缀 `updates/gxt/`**：复用发布用的 `updates/` 前缀（本就匿名公读、可写），零控制台配置。
  CAM 写权限精确到 `updates/gxt/*`，不能放宽（否则把 `latest.yml` 与安装包一并交出去）。
- **凭证**：`shareConfig.js`，缺失时回退环境变量 `COS_SECRET_ID/KEY/BUCKET/REGION`。
  开发机可直接发；分发给终端用户的安装包需内置 `shareConfig.js`。
- `putSnapshot(payload)` **本身就是通用的**——它 PUT 任意 JSON，不认识内容语义。
- 收口在云函数：`importGxtSnapshot` 硬校验 `snap.kind !== 'gxt-snapshot'` 就拒收。**这是唯一要改的地方。**

### 1.2 平台侧的配置模型（v1.4.2 之后）

一份配置 = **一张链路表 + 三个全局资源库的引用**：

```
config.state = {
  rows: [ { stationId, rxStationId, basebandId, …所有 target:'link' 的字段 }, … ],
  satId: 'sat3'                       // 一份配置 = 一颗卫星
}
全局库（不随配置走）：地球站 es / 载波 carrier / 卫星 sat，条目形如 { id, name, nameAuto, form, grd?, ngsoSat? }
```

字段的归属由 `params.js` / `ngsoParams.js` 的 `target` 声明：
`'sat'` → 卫星库条目，`'link'` → 行，`'op'` → 求解策略（不进引擎），`'meta'` → 库引用。

摊平函数已存在：`buildParams(satForm, carrierForm, txStation, rxStation, txEs, rxEs)`
→ `{ satParams, linkParams }`。

### 1.3 小程序侧的配置模型

一份配置 = **一组 satelliteParams + 最多 8 条 linkParams**，全部扁平内嵌，无库概念：

```js
{ configName, satelliteParams:{…}, linkParams:{ 1:{…}, …, 8:{…} },
  calculationResults, noiseRatioMode, markedParams, highlightedRows }
```

默认值见 `miniprogram/app.js` 的 `getDefaultSatelliteParams()` / `getDefaultLinkParams()`。
云端存取 `cloudfunctions/configManager`，`save` **不做字段白名单**——整块 `satelliteParams` /
`linkParams` 原样落库。**所以配置侧的云函数一行都不用改。**

已有的导入路径（`configs.js` 的 `importFromBase64`）证明了模型：解析 JSON → 校验
`satelliteParams && linkParams` → `configManager.save` → 失败回退 `wx.setStorageSync('savedConfigs')`。
新通道只是把「Base64 分享码」换成「密钥 + COS」，落地那一段可以逐行照抄。

### 1.4 频率计划模型与渲染

- 模型 `src/shared/freqPlanModel.js`：`{ id, name, satFolder, satName, band, bandAuto, note, los[], beams[], channels[], updatedAt }`，内部一律 MHz。
- 存储 `electron/services/freqPlan.js`：`userData/freq-plans/<id>.json` + `index.json`。
  **主进程只存字节，不认识语义**——模型/校验/容量全在渲染端。
- 渲染 `src/shared/freqPlanRender.js`：`layout(plan, style)` 出**纯几何**，`toSvg()` 再画。
  「一套几何两处用」——屏上命中测试与导出 PNG 吃的是同一份 layout。
- 文件区已有 `freqPlan.exportFile('json', …)` / `importJson()`，导出入口是现成的。

### 1.5 小程序侧「可视化工具」

`pages/index/index.wxml` 的浮层面板，现有六项：AR对星 / 卫星覆盖 / 星间链路分析 / 星座地图 /

## 2. 通道设计：一条通道，三种载荷

### 2.1 信封

一个密钥 = 一个包，包里可以装多件。与 `LbShareDialog` 现有的「勾选 N 个配置 + M 条库条目」
一次分享同构，也与它「导入一律先出包内清单」的口径一致。

```jsonc
{
  "kind": "satsim-pack",         // 云函数按此放行
  "v": 1,
  "from": "SatSim v1.4.x",       // 平台版本，用于口径差提示（见 §6.2）
  "ts": 1754000000000,
  "expiresAt": 1756592000000,    // 可选；云函数据此判过期
  "name": "中星10R Ku 前向",       // 包名，小程序清单页显示
  "items": [
    { "type": "lb-config",  "name": "…", "mod": "GEO",  "config": { /* §3 */ } },
    { "type": "lb-config",  "name": "…", "mod": "NGSO", "config": { /* §3 */ } },
    { "type": "freq-plan",  "name": "…", "plan": { /* §4 */ }, "layout": { /* §4 */ } }
  ]
}
```

`kind: 'gxt-snapshot'` 原样保留，老版本平台发出的包照收不误。

**`importGxtSnapshot` 就是卫星覆盖页那个密钥导入函数，已部署且在用**——通道是活的，
二期可直接联调，不必再走一遍「先部署云函数」。

**扩它、不另起一个新函数**：`COS_BASE`（桶 / 地域 / 前缀）必须与 `share.js` 的写入路径逐字一致，
两个函数就是两份要同步的副本，迟早漂。改动是一处 kind 白名单 + `meta` 分支，
`kind:'gxt-snapshot'` 的行为逐字不变，老版本平台发出的覆盖快照照收——
但**动的是正在用的函数，改完必须先回归一次卫星覆盖的密钥导入**再上频率计划。

### 2.4 大小：唯一的硬约束

微信云函数**返回值上限 1 MB**，而现在的实现是把快照内联在 `data` 里返回。估算：

- 链路配置：一份 8 链路配置 ≈ 20 KB。不成问题。
- 频率计划：`plan` 约 30~60 KB（94 波束 HTS）；`layout` 约 200~400 KB。常规计划无压力，
  **大型 HTS 计划有触顶风险**。

分级方案（按需启用，不要一上来就上）：

1. **瘦身**：`layout` 坐标取 2 位小数、键名缩写、只保留绘制与命中必需的字段。
2. **压缩**：平台 PUT 时 gzip，云函数原样透传 `{ gz: base64 }`，
   小程序用**已内置的 `pako_inflate`** 解压。JSON 压缩比 5~10×，一步到位。
3. **兜底**：平台发送前估算 payload 大小，超过 ~800 KB 时明确拒绝并提示拆分。

**落地实测（2026-08-01）：只做了 1 与 3，2 用不上。**

| 用例 | 整包 |
|---|---|
| 一份链路配置 | 2.3 KB |
| 24 转发器 + 3 波束 + 4 载波 | 43 KB |
| **94 波束 + 48 转发器 + 120 载波（中星26 量级）** | **183 KB**（draw 52 · chs 48 · beams 22 · alloc 61） |

原估的「`layout` 约 200~400 KB」没有成真，因为送的不是 `layout()` 那个对象，而是**它摊平出来的
绘制指令**（`{k:'r',x,y,w,h,f}` 这种，键名压到一个字符）—— `layout()` 里大半是排版过程中的簿记
（`segs` / `laneY` / `baseSegs` / 每个 block 上挂的 `raw`…），画图一个都用不着。
拒发线定在 900 KB（`miniPack.SIZE_MAX`），640 KB 起提示一句。

### 2.5 密钥与生命周期

- 密钥 8 位、字母表 31 个字符 → 31⁸ ≈ 8.5×10¹¹。对象不可列举，密钥即凭证。
  枚举不现实，但**对象是匿名公读的**，而链路配置含站址与工程参数——知晓即可，沿用 8 位。
- **对象无 TTL，会一直堆积。** 建议二选一：桶上加 lifecycle 规则（`updates/gxt/` 前缀 N 天过期），
  或信封里放 `expiresAt` 由云函数判并回「已失效」。后者不依赖控制台操作，优先。

## 3. 载荷一：GSO / NGSO 链路配置

### 3.1 总体映射：一条链路 = 一份小程序配置

（2026-08-01 用户拍板）

**★ 小程序里一份配置就是一条链路** —— 这是产品口径，写死在这里，后面所有映射据此推。
`linkParams` 那个 1~8 的键是**工作台上的 8 个草稿位**，不是「一份配置里有 8 条链路」；
存一份配置就是把当前这条存下来。

```
平台一份配置（1 颗卫星 + N 行链路 + 三库引用）
   ↓ 逐行摊平：行 ⊕ 地球站条目.form ⊕ 载波条目.form ⊕ 卫星条目.form
N 份小程序配置，每份 = satelliteParams + linkParams{ "1": 该行 }
```

平台的一行本来就是一条自洽链路（自带发信站/收信站/载波/工作点），逐行拆与两边的语义都对得上，
N>8 的切分问题也就不存在了。

- **配置名**：`<平台配置名> · <发信站>→<收信站>`；同名冲突再追加行号。
- **只写 `"1"` 一个槽**，不铺 2~8。铺默认值等于凭空造 7 条假链路，铺副本更糟。
- **`satelliteParams` 每份都带一份完整的**（同一颗星重复 N 遍）——小程序没有「共享卫星」的
  概念，重复是对的。

⚠ **由此带出小程序侧要补的一行兜底**：`pages/index/index.js:703` 的
`linkParams: app.globalData.linkParams[linkNum]` **没有兜底**，而配置载入是
`app.globalData.linkParams = config.linkParams` 整块替换（`configs.js:1283/1335/1414/1465/2449`
四处同款，均无规整）。于是载入一份单槽配置后再点链路 2，`this.data.linkParams` 被置成
undefined，界面绑定全断。

→ 改成 `app.globalData.linkParams[linkNum] || app.getDefaultLinkParams()`。
这**不是为本功能开的口子**：现有的 Base64 分享码导入同样能带进单槽配置，这个白屏本来就够得着，
只是本功能会让它变成常态。`onShow`（`index.js:505`）那一处已有 `&&` 兜底，只有 `switchLink` 漏了。

### 3.2 字段对照（GSO）

**同名直通**（占绝大多数，无需转换）：

- 卫星：`satelliteName` `orbitPosition` `frequencyBand` `sfdRef` `sfdGtRef` `transponderBandwidth`
  `BOi` `BOo` `xpdrIntermodFactor` `aci/adj/xpol UplinkFactor` `hpaIntermodFactor` `aci/adj/xpol DownlinkFactor`
- 上行：`earthStationLocation` `antennaDiameter` `longitude` `latitude` `altitude` `centerFrequency`
  `uplinkPolarization` `G_Ts` `rainRate` `antennaEfficiency` `paBackoff` `feederLoss`
  `uplinkPowerControl` `upcValue` `uplinkOtherLoss` `uplinkAvailability`
- 下行：`rxEarthStationLocation` `rxAntennaDiameter` `rxLongitude` `rxLatitude` `rxAltitude`
  `rxCenterFrequency` `downlinkPolarization` `rxEIRP` `rxRainRate` `rxAntennaEfficiency`
  `rxAntennaNoiseTemp` `rxReceiverNoiseTemp` `rxFeederLoss` `downlinkOtherLoss` `rxDownlinkAvailability`
- 载波：`infoRate` `modulation` `fec` `rsCode` `m` `bandwidthFactor` `ber` `ebno` `margin` `noiseRatioMode`

（`upcValue` 小程序的 `getDefaultLinkParams()` 里没有，但 `linkCalculator.js:804` 确实读它——照发即可。）

**平台有、小程序没有**：

| 平台字段 | 处理 |
|---|---|
| `rxAntennaNoiseTempMode = 自动` | 小程序无此开关。把**平台算出的天线噪温数值**写进 `rxAntennaNoiseTemp`，否则小程序按 35 K 默认算，差几 K 直接体现在 C/N |
| `calcMode` ∈ margin/power/balance/overbalance | 见 §3.3 |
| `overDb`（功带平衡下超发量） | 小程序无对应 → 降级为功带平衡，写进 `notes` |
| `paPowerW`（功放功率预设） | 仅 `calcMode='power'` 时映射到 `inputPaPower` |
| 库条目名 / `nameAuto` | 折进 `configName` 与 `notes`，不进参数 |
| GRD 方向图匹配、频率计划引用（`grd.satFolder` / `fpId`） | **一律剥掉**（同 `lbShare.js` 的 sanitize 口径：那是发送方机器上的节点 key）。它们回填出的 `G_Ts` / `rxEIRP` / 频率极化带宽是**数值**，照常带走 |

**小程序有、平台没有**：

| 小程序字段 | 处理 |
|---|---|
| `beamInput`（波束名，纯文字） | 不参与计算（`linkCalculator` 未读）→ 填卫星条目名或 GRD 波束名 |
| `deltaTheta`（邻星间隔） | 平台 UI 无此字段，但**两侧引擎空回退都是 2.5**（`packages/core/utils/linkCalculator.js:417`）→ 留空即可，无口径差 |
| `dvbStandard` / `modcodIndex` | 平台直填 `ebno`+`fec` → 送 `'custom'` / `-1`，让小程序按数值走 |
| `rateCalcMode` / `symbolRate` | 送 `'infoRate'` / `'--'` |
| `marginMode` | 由 `calcMode` 推出（见 §3.3） |

### 3.3 计算方式的枚举翻译

| 平台 `calcMode` | 小程序 `calcMode` | 小程序 `marginMode` | 备注 |
|---|---|---|---|
| `margin`（给余量算功放） | `reverse` | `manual` | 默认路径 |
| `power`（给功放算余量） | `forward` | `manual` | `inputPaPower ← paPowerW` |
| `balance`（功带平衡） | `reverse` | `balanced` | |
| `overbalance`（平衡下超发 `overDb`） | `reverse` | `balanced` | **有损**：超发量丢失，须写进 `notes` |

### 3.4 两个必须绕开的坑

**坑 1：`sfdRef` 会被折算两次。**
`buildParams()` / `splitForm()` 在返回前做了引擎入口换算 `sfdRef = sfdRef + sfdGtRef`，
而小程序内部的 `_engineSatParams` 会**再折一次**。直接把 `buildParams()` 的输出塞进
`satelliteParams`，SFD 就多加了一个 `sfdGtRef`。
→ 导出必须走 **form 原值**：新写一个 `toMiniParams()` 镜像 `buildParams` 的 `target` 分流逻辑，
但**不做那一步折算**。同时 `sfdRef` 与 `sfdGtRef` 都要送，让小程序自己折。

**坑 2：Vue 响应式代理过不了 IPC。**
`config.state.rows` / 库条目 `form` 都是 reactive 的，直接经 IPC 结构化克隆会当场抛
`An object could not be cloned`，且没有 catch 时**全静默**。出 IPC 前 `JSON.parse(JSON.stringify(x))`
（`buildParams` 结尾正是这么做的）。

### 3.5 NGSO 专属

小程序 NGSO 的几何模型是「每站各自的最低仰角 + 轨道高度（或直接给斜距）」：
`minElevation` / `distanceMode('altitude'|'slantRange')` / `orbitAltitude` / `slantRange`，收信站侧同构加 `rx` 前缀。

平台 NGSO 的几何要强得多——SGP4 双站互视 + 逐候选跑真实引擎按瓶颈侧取最差路径。
**若只送 `orbitAltitude` + `minElevation`，小程序会用自己的闭式几何重算，与平台的最差路径不是一回事。**

→ 送**平台算出来的那组几何**，让小程序原样用：

```js
distanceMode: 'slantRange',   slantRange:   <平台最差路径的上行斜距 km>,
rxDistanceMode: 'slantRange', rxSlantRange: <平台最差路径的下行斜距 km>,
minElevation:   <该时刻发信站实际仰角>,      // 小程序的大气/雨衰按仰角走，必须同步
rxMinElevation: <该时刻收信站实际仰角>,
orbitAltitude / rxOrbitAltitude: <轨道高度>   // 留作显示与回退
```

平台内部本来就是「用注入的 `slantRange` 覆盖」的路子（见 `ngsoParams.js` 尾部注释），
取值现成。另外：

- `satelliteParams.orbitType = 'NGSO'`，`ngsoOrbitClass` 用 `src/shared/orbitClass.js` 判定。
  该函数出 `GEO|IGSO|MEO|LEO|HEO` 五档，小程序只有 LEO/MEO/HEO 三档 → **IGSO 归 HEO**
  （小程序里这个字段只影响轨道高度预设，不进计算，属显示性归并）。
- 轨道取星来源（`ngsoSat.folder`）是本机指针 → 剥掉，同 §3.2。

### 3.6 结果一并带走（重要）

小程序的配置模型自带 `calculationResults` 字段。**把平台算出的结果填进去**，并在信封里标
`from`（平台版本）。理由见 §6.2——两边的数**不会完全相同**，与其让用户在小程序里点一次
「计算」然后困惑，不如把平台值随配置带过去，小程序详情页原样显示；用户主动重算后覆盖为小程序值。

## 4. 载荷二：频率计划

### 4.1 送什么

```jsonc
{
  "type": "freq-plan",
  "name": "中星26 前向 Ka",
  "plan":   { /* freqPlanModel 的原样 JSON，小程序端不解析结构，只按需取字段显示 */ },
  "layout": { /* freqPlanRender.layout(plan, style) 的输出，坐标 2 位小数 */ },
  "meta":   { "unit": "MHz", "summary": "…", "colors": […] }
}
```

`plan` 走 `freqPlan.get(id)` 的原样内容（`normalizePlan` 保证自洽）。
`layout` 由平台在发送那一刻现算，标明是派生物。

### 4.2 为什么**不**在小程序重算版式

`layout()` 依赖 `resolveAll()` 一整套口径：LO 推算与 cross-strap 解耦、波束占段的
`tile | stack | full` 三路、`pickLane` 分层、断口折叠、频带外不出片……这套口径 2026-07~08
连改三轮（波束起止上提到波束身上、装不下改同频叠放、`stripes[0]` 空数组崩溃）。

在小程序照抄一份 = 第二份真相，**必漂**。这份代码在「单位=整份计划的刻度」上已经吃过
一次同样的亏（图与表两处各写一遍，同一个量同屏两个数）。

→ **小程序只做三件事**：按 `layout` 画、按命中矩形认点击、按 `plan` 显示明细。
零算法、零单位换算逻辑，平台改版式小程序自动跟随（重新导入即可）。

代价是诚实的：**小程序看到的是导入那一刻的版式**，平台后续改了计划要重发。
考虑到「只能从仿真平台导入」的定位，这个代价是对的。

### 4.3 `layout` 需要携带什么

- 画：块的 `x/y/w/h` + 填色 + 边框 + 块内文字（编号/频率标注/极化行标签/图例/LO 箭头几何/断口）
- 命中：每块的矩形 + 它对应的 `channelId`；图例每项的矩形 + `beamId`
- 尺寸：`width/height`（小程序按容器宽做等比缩放，缩放只改 canvas transform，不重排）

`layout()` 现有输出已基本覆盖（屏上编辑器就靠它做命中测试与拖拽）。要确认的是**文字有没有全部
落进 layout**，还是有一部分在 `toSvg()` 里现拼——若是后者，把那部分下沉进 `layout()`，
平台自己也受益（「一套几何两处用」本来就是这个模块的立意）。

## 6. 风险与诚实边界

### 6.1 单向，不可回流

小程序侧的配置是扁平的，回传平台无法还原三库结构与引用闭包。
**明确定为单向**：平台 → 小程序。频率计划更是「只能从平台导入」。

**导入后的配置允许在小程序内再分享**（2026-08-01 用户拍板）——落进 `user_configs` 之后
它与用户自建的配置无差别，现有 `configManager.share` / `batchShare` 直接可用，零改动。
代价知晓即可：平台参数会经小程序的分享码二次扩散，且**扩散出去的是摊平后的副本**，
与平台库里的原件此后各走各的（对端改了小程序里那份，平台这边不知道）。

### 6.2 两边的数会不一样 —— 这是最需要说清的一条

平台这一年修了 14 项科学性问题（云噪入 T_sys、XPD 标度、P.676 低仰角、P.618 §8 全链路、
瀑布归因…），基线已重锁在 12.99 / 12.84；小程序没有跟进这些。
**同一份参数，两边算出的余量会有差**（NGSO 侧因 §8 与最差路径口径差得更多）。

对策，三条一起上，缺一条都会让人误以为一致：

1. 配置里带平台的 `calculationResults`（§3.6）；
2. 信封里带 `from`（平台版本），小程序详情页把结果标注为「平台计算值」；
3. 用户在小程序点「计算」后，结果换成小程序自己算的——**不做静默对齐，也不假装一致**。

### 6.3 其余

| 风险 | 处置 |
|---|---|
| 云函数 1 MB 返回上限 | §2.4 三级方案；先做瘦身，触顶再上 gzip + pako |
| 改动的是在用的云函数 | 改完先回归卫星覆盖的密钥导入，再上频率计划（§2.3） |
| COS 对象无限堆积 | 信封加 `expiresAt`，云函数判过期（不依赖控制台） |
| 打包给终端用户缺 `shareConfig.js` | 现有 `scripts/check-share-config.mjs` 已在发版时告警，沿用 |
| 密钥公读 | 8 位不可枚举，但对象匿名可读；链路配置含站址，知晓即可 |
