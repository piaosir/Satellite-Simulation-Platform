# 星历导入与轨道向导

本文是这两件事的口径说明：平台能收哪些星历、收进来以后按什么模型算、精度边界在哪里；
以及轨道向导九种类型各自解什么、公式是哪一条。

---

## 1. 两种传播类型

平台里一颗星只有两种传播方式，界面与代码里的叫法一一对应：

| 界面 | 代码 | 数据 | 传播 | 时段 |
|---|---|---|---|---|
| （不单列，就是普通卫星） | `orbitType:'omm'` / `'elements'` | 平均根数 | SGP4 / SDP4 | 无限制 |
| **星历点序列** | `orbitType:'ephem'` | 时间标签位置序列 | 插值（Lagrange / Hermite） | **只在采样时段内** |

「星历点序列」的口径一句话：**时间标签位置序列，按插值取位，不做轨道外推**。
查询时刻落在采样时段之外时该星**不画、不参与任何几何**（返回 null），不外推、也不钉在端点。

两者的取位入口是同一个：核心侧 `packages/core/utils/orbitPos.js` 的 `positionAt`，
渲染侧 `src/viz/constellation/satPos.js` 的 `posAt`。全平台不许再直接调 `sat.propagate`——
表对象不是 satrec，喂给 SGP4 不报错、只会得到垃圾坐标，这种错一眼看不出来。

## 2. 收得了哪些格式

### 2.1 平均根数（走 SGP4，落 `gp` 组）

| 格式 id | 说明 |
|---|---|
| `omm-csv` / `omm-json` / `omm-kvn` / `omm-xml` | CCSDS OMM 的四种写法 |
| `tle` / `3le` | 两行 / 三行定长卡片 |
| `yuma` / `sem` | **GPS 年历**，换算成 OMM 记录后走同一条 SGP4 通路 |

前六种由 `packages/core/utils/ommFormats.js` 承担（本次一个字没改）；
年历由 `packages/core/utils/gpsAlmanac.js` 换算。

### 2.2 时间标签位置序列（走插值，落 `ephem` 组）

| 格式 id | 说明 |
|---|---|
| `stk-e` | STK `.e`（`BEGIN/END Ephemeris`） |
| `ccsds-oem-kvn` | CCSDS 502.0-B OEM，关键字=值 |
| `ccsds-oem-xml` | CCSDS 505.0-B NDM/XML 的 `<oem>` |
| `sp3` | SP3-c / SP3-d 精密星历（IGS 及各分析中心产品） |

全部**按内容嗅探**（`detectFormat`），扩展名只作兜底；所有入口统一剥 BOM。

### 2.3 拒收清单（会点名报错，不静默吞）

- `.e`：`CentralBody` 不是 Earth；`CoordinateSystem` 不在下表；`DistanceUnit` 不是 Meters/Kilometers/Feet；
  `TimeFormat` 不是 EpSec/UTCG/ISO-YMD/JDate/YYDDD。
- OEM：`CENTER_NAME` 不是 EARTH；`REF_FRAME` 不在下表；`TIME_SYSTEM` 不是 UTC/TAI/TT/GPS/TDB；
  同一颗星的多段参考系不一致。
- SP3：首行不是 `#c` / `#d`。
- 通用：整星没有有效采样点、或全组都无效。

## 3. 坐标系与时间系统

### 3.1 参考系

链路（`packages/core/utils/frames.js`）：

```
J2000 --IAU-76 岁差--> MOD --IAU-80 章动--> TOD --R3(-Eq.Eq)--> TEME --R3(GMST)--> ECEF
```

- `ICRF` / `GCRF` 与 J2000 差 mas 级，**视同 J2000**。
- `TEME -> ECEF` 只用 GMST，与 `vendor/satellite.js` 的 `gstime` / `eciToEcf` **逐位同口径**——
  平台既有口径是「卫星位置 = TEME，经 gstime 落地」，外部星历必须换到 TEME 才进得了现有管线。

各格式的帧名映射：

| 来源写法 | 本平台 |
|---|---|
| `J2000` / `EME2000` / `ICRF` / `GCRF` / STK 的 `Inertial` | J2000 |
| `MeanOfDate` / `MOD` | MOD |
| `TrueOfDate` / `TOD` | TOD |
| `TEME` / `TEMEOfDate` | TEME |
| `Fixed` / `ECEF` / `EFG` / `ITRF*` / `IGS14` / `IGb14` / `IGS20` | Fixed（地固） |

`.e` 的 `EphemerisLLATimePos` / `EphemerisLLRTimePos` 两种块**按定义就在地固系**，与 `CoordinateSystem` 无关。

### 3.2 时间系统

内部一律 UTC 毫秒。闰秒表在 `packages/core/utils/timeSystems.js` 的 `LEAP_SECONDS`，
**新增闰秒只改这一处**（截至 2026-09 最后一次是 2017-01-01 的第 37 秒）。

```
TAI − UTC = 闰秒      GPS = TAI − 19 s      TT = TAI + 32.184 s
TDB ≈ TT              BDT = GPS − 14 s      UT1 ≈ UTC
```

`.e` 的时间写法四档：EpSec（相对 ScenarioEpoch）/ UTCG / ISO-YMD / JDate。
SP3 的 `%c` 行第 10–12 列给时间系统（GLO 已折算到 UTC；GAL / QZS / IRN 与 GPS 同原点）。

## 4. 精度边界（诚实的那一版）

| 事项 | 量级 | 出处 |
|---|---|---|
| J2000 → TEME | **0.94 m**（Vallado Example 3-15 实测；含 δΔψ/δΔε 的原文值差 50 m 以内） | `frames.test.mjs` |
| TEME → ECEF | **261 m**（忽略 ΔUT1 与极移所致；上限按 1 km 记） | 同上 |
| 插值：LEO 60 s 采样 Lagrange-6 | **< 1 m**（实测 0.32 m / 24 h） | `ephemInterp.test.mjs` |
| 插值：MEO 900 s 采样 Lagrange-10 | **< 0.5 m** | 同上 |
| 同格式导入 → 导出 | 时间到 μs、位置到 **1e-9 km** 逐位相同 | `ephemFormats.test.mjs` |
| 跨帧导出 → 再导入 | 取位差 **≤ 1 m** | 同上 |
| SGP4 星采样 → 导出 → 回读插值 | 与 SGP4 差 **≤ 10 m**（60 s 步长） | `ephemParity.test.mjs` |

**明确忽略的两项**：ΔUT1（|ΔUT1| ≤ 0.9 s）与极移（≤ 0.3"）。合计使 ECEF 方向误差 ≤ 1 km 量级；
惯性侧不受影响。将来要做米级 ECEF，须引入 IERS EOP，届时只改 `frames.js` 一处。

**采样步长的合理性**：`h·n > 0.3 rad` 即插值不可信（附录 C 的判据），建表时会给「过粗」告警。
LEO 用 900 s 采样就属于这一类；SP3 的 15 min 采样在 MEO 上是 cm 级、在 LEO 上没有意义。

**GPS 年历的精度**：年历本就是供接收机捕获用的粗根数。换成 OMM 再走 SGP4 与 ICD 年历算法
（ICD-GPS-200 表 20-IV，纯开普勒、一点 J2 都没有）在 ±3 天上差几十公里——
这是两个**轨道模型**的差，不是换算错：拿换算出来的根数做纯二体传播与 ICD 对比，在 toa 上差 **4.6 m**。
要精密轨道请用 SP3（cm 级，走点序列通路）。

## 5. 各消费方对「星历点序列」的态度

| 模块 | 支持 / 拒收 |
|---|---|
| 3D / 2D 地图点云、信息卡、聚焦几何（轨道线 / 星下点轨迹 / 覆盖圈 / 锥）、可见性分析 | **支持** |
| 搜索池 → NGSO / 再生 / 端到端窗口（最差几何、斜距工具、链路视图） | **支持**。扫描时窗与采样时段取交，无交集报「星历时段 A → B 与分析时段 … 不重叠」 |
| 对星覆盖（壳层）、CI 时变 C/I、小程序发送、SSA 报告、日凌「星历」档 | **拒收**，给一句状态、不进计算 |

渲染端与各引擎消费点序列时只传**引用** `{type:'ephem', ref:{groupId, key}}`——
表几 MB，绝不进配置文件与 IPC 参数；主进程在进 core 之前按 ref 取表换成 `samples`。
core 拿不到表会**点名报错**，不会静默退成 SGP4。

## 6. 存储

- 组清单：`userData/data/omm/custom.json`（每组带 `kind` / `visible` / `color` / `format`）。
- 点序列的采样：`userData/data/ephem/<组id>.json`，**按 TEME 存**（渲染端与各引擎要的就是它）。
  导出时再换回组的原帧——换帧来回误差 ~1e-12 km，远在 1e-9 km 的打印分辨率以下。
- 点序列星的合成 NORAD：**800000 段**，每组占 10000；GPS 年历查不到编号时用 990000+PRN。
- 删组连采样文件一起删。

## 7. 轨道向导

九种类型（按 STK Orbit Wizard 的顺序）与各自的输入：

| 类型 | 输入 | 解出 |
|---|---|---|
| 圆轨道 | i、h、Ω | e=0、ω=0、M₀=0 |
| 临界倾角 | 方向（顺行 63.4349° / 逆行 116.5651°）、hₐ、hₚ、λ_AN、ω | a、e；Ω = λ_AN + GMST(t₀) |
| 临界倾角·太阳同步 | hₚ、λ_AN、ω | i 强制 116.5651°（顺行无解，见下）；由太阳同步条件解 e |
| 地球同步 | 星下点经度 λ、i | a = 42164.17 km、e=0 |
| Molniya | 远地点经度 λₐ、hₚ、ω | i=63.4349°、a=26561.8 km、M₀=180° |
| 回归轨道 | i、k、m、λ_AN | e=0；a 由 k·T_Ω(a) = m·2π/(ω_e − Ω̇(a)) 求根 |
| 回归·太阳同步 | k、m、λ_AN、LTAN 或 LTDN | e=0；T_Ω = m·86400/k；a 与 i 联立 |
| 太阳同步 | i **或** h（二选一）、LTAN 或 LTDN | e=0；cos i 公式 |
| 自定义根数 | 六根数（原来那套表单） | 原样 |

公式全在 `src/viz/constellation/orbitDesign.js`，J2 一阶长期项：

```
n = sqrt(mu/a³)，p = a(1−e²)
Ω̇ = −(3/2)·n·J2·(Re/p)²·cos i
ω̇ =  (3/4)·n·J2·(Re/p)²·(5cos²i − 1)
Ṁ =  n·[1 + (3/4)·J2·(Re/p)²·sqrt(1−e²)·(3cos²i − 1)]
交点周期 T_Ω = 2π/(Ṁ + ω̇)
太阳同步：cos i = −(2/3)·Ω̇_ss·(1−e²)²·a^{7/2}/(J2·Re²·sqrt(mu))
```

三处值得记下的口径：

1. **临界倾角·太阳同步只能取逆行**。顺行的 63.43° 的 cos i > 0、节点西退，
   与太阳同步要的东进方向相反，根本无解。
2. **Molniya 的 a 按开普勒半恒星日关系算**（26561.76 km），不按含 J2 的交点周期
   （那会得 26560.67 km）——前者与 e=0.741、远地点 39870 km 三者自洽。
3. **地方时一律平太阳时**：用太阳平黄经 L₀（Meeus 25.2 一次式），与视太阳相差时差方程（≤16 min）。

解出来的根数最终都收敛成既有的 `params`，交给 `generateConstellation` 铺开——
**walker.js 的生成逻辑一个字没改**，向导只是换了一种输入方式。
布局四档：单星 / Delta / Star / 单轨道面；单星时 T=P=1 且名字不加 `-Pxx-Sxx` 后缀。

存档带 `design:{type, inputs}` 供再编辑回显；**旧存档没有 `design` 时一律当「自定义根数」**，
行为与从前逐字一致。
